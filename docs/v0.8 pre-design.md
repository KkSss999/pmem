# v0.8 前置设计决策：Hybrid Recall Engine

> 状态：draft → 待评审锁定
> 日期：2026-07-03
> 依据：`decision.project_rag_os_positioning_20260626`、`decision.structure_first_hybrid_recall_20260626`、`decision.sqlite_first_semantic_layer_20260626`、`feature.v0_8_hybrid_recall_engine_20260626`、`task.rag_research_sprint_20260626`

## 一、背景与问题

v0.7.x 的检索现状（代码审计结论，2026-07-03）：

1. **逻辑重复**：`src/commands/ask.ts` 与 `src/core/query/ask.ts` 各自维护一份相同的 6 步检索（id → alias → tag → graph 1-hop → FTS/LIKE fallback），已经开始漂移风险。
2. **排序原始**：只按 match_type 枚举硬排序 + 静态 confidence 常量，无组合打分。
3. **信号缺失**：
   - `paths` 表的 source_file 关系完全未参与 ask 检索——"我在改 src/core/db.ts，相关记忆是什么"这类最高价值查询无法命中；
   - 无时近性（recency）信号，三个月前的过期决策与昨天的活跃决策同权；
   - 无 stale/dirty 惩罚，`dirty_flags` 与 `last_verified_at` 未参与排序；
   - FTS5 五列（title/summary/body/aliases/tags）未使用 bm25 字段权重，正文噪音词与标题精确命中同权。
4. **FTS 只是 fallback**：仅当前 5 步零命中时才启用，正常查询根本走不到全文检索——精确信号与文本信号是"或"关系而非融合关系。
5. **无解释性**：输出只有 match_type，Agent 无法判断"为什么召回这张卡、该信任多少"。
6. **预算是截断不是分层**：`formatOutput` 末端硬截断，没有 L0-L3 分层渲染，预算紧张时丢的是尾部而非最低价值内容。

v0.8 目标：**把"能存项目记忆"升级为"能按任务精准恢复项目上下文"**。

## 二、产品目标

### 2.1 一句话目标

一个查询进来，pmem 产出一个**有界、确定、可解释、按预算分层**的召回集。

### 2.2 成功标准

1. 精确信号查询（card ID、文件路径、决策标题、tag）100% 首位命中；
2. 模糊关键词查询经 FTS+融合排序后 top-3 命中相关卡片；
3. 同一查询在索引未变时输出确定（可复现、可测试）；
4. 每条召回结果附带机器可读的 reasons 数组；
5. stale/dirty 卡片被降权但不被隐藏（附 penalty 说明）；
6. 预算裁剪按 L0→L3 分层进行，L0 永不被裁。

### 2.3 范围排除（v0.8 不做）

- ❌ 向量数据库 / embedding（→ v1.1.1 SQLite-first semantic layer）
- ❌ LLM rerank / contextual retrieval（→ v1.1.2）
- ❌ Web UI（已推迟）
- ❌ 新增 MCP 工具面（现有 pmem_ask / pmem_context 直接受益于底层升级，不加新工具）
- ❌ 卡片正文 chunking（v0.8 以整卡为召回单元；trace 已有结构化解析）

## 三、架构设计

### 3.1 检索管线

```
query (+ optional task context)
  ↓
[1] Intent parse         — 识别查询中的精确信号：card-id 形态、文件路径形态、
                            类型词（decision/module/...）、CJK/英文 token
  ↓
[2] Candidate generation — 多路并行召回，每路给出 channel 原始分：
      a. exact id / id-substring
      b. alias
      c. tag（exact + token）
      d. source_files 路径匹配（paths 表，新增）
      e. FTS5 bm25 字段加权（title 4.0 / aliases 3.0 / tags 2.5 / summary 2.0 / body 1.0，
         常态启用，不再只做 fallback；无 FTS5 时回退 LIKE）
  ↓
[3] Graph expansion      — 对 top 种子做 1-hop 扩展（可配 2-hop），
                            继承分 = 种子分 × edge_confidence × 距离衰减(0.5/hop)
  ↓
[4] Scoring / fusion     — 组合打分（见 3.2），跨路去重取最高分并合并 reasons
  ↓
[5] Budgeted rendering   — L0-L3 分层渲染（见 3.3）
```

### 3.2 打分模型

每张候选卡的最终分：

```
score = base                    // 候选生成通道的原始分
      × type_weight             // 卡类型权重
      × recency_factor          // 时近性
      × staleness_penalty       // 过期惩罚
      × status_factor           // 卡状态
```

| 因子 | 取值 | 说明 |
|---|---|---|
| base: exact_id | 1.0 | 全等命中 |
| base: exact_title / id-substring | 0.85 | |
| base: alias | 0.9 | |
| base: tag exact / token | 0.7 / 0.6 | |
| base: source_file exact / prefix | 0.9 / 0.75 | 新增通道 |
| base: fts | 0.3–0.8 | bm25 归一化：`0.3 + 0.5 × norm(-bm25)` |
| base: graph | 种子分 × conf × 0.5^hop | |
| type_weight | decision/module 1.1，task/feature/risk 1.0，trace 0.85 | manifest 可覆盖 |
| recency_factor | `0.75 + 0.25 × exp(-age_days/90)` | updated_at 距今；90 天半衰 |
| staleness_penalty | dirty_flag 未解决 ×0.7；last_verified 早于 updated_at ×0.9 | 降权不隐藏 |
| status_factor | active/draft 1.0，superseded/archived 0.5，deprecated 0.3 | |

**确定性要求**：同分 tie-break 按 card id 字典序。`Date.now()` 只在入口取一次传入纯函数，保证可测试。

### 3.3 预算分层渲染（L0-L3）

| 层 | 内容 | 预算策略 |
|---|---|---|
| L0 | 项目一句话、stage、focus、next | 永不裁剪 |
| L1 | active foundation / key decisions 压缩摘要 | 预算 ≥800 时保留 |
| L2 | 与 query 强相关的卡片摘要（top-N by score） | 按分数从低到高裁 |
| L3 | READ_IF_NEEDED 路径列表 | 只有路径，成本极低，尽量保留 |

裁剪顺序：L2 低分项 → L2 摘要变一行 → L1 压缩 → L3 截断。L0 永存。

### 3.4 explain 输出

每条召回项：

```json
{
  "id": "decision.structure_first_hybrid_recall_20260626",
  "score": 0.81,
  "reasons": [
    {"channel": "tag", "detail": "matched tag: hybrid-search", "base": 0.7},
    {"channel": "fts", "detail": "bm25 title+body", "base": 0.62}
  ],
  "factors": {"type_weight": 1.1, "recency": 0.96, "staleness": 1.0, "status": 1.0},
  "graph_distance": 0,
  "stale": false
}
```

compact 格式渲染为单行：`- decision.xxx (0.81) [tag:hybrid-search, fts]`。

### 3.5 代码结构

```
src/core/query/
  engine/
    intent.ts      — 意图解析（纯函数）
    candidates.ts  — 多路候选生成（依赖 db）
    scoring.ts     — 打分融合（纯函数，可单测）
    pack.ts        — L0-L3 预算渲染（纯函数）
  ask.ts           — 重写为 engine 编排（保持 AskResultV03 出参兼容 + 新增 explain 字段）
  context.ts       — 复用 engine，task-aware
  recall.ts        — 接入 pack.ts 分层渲染
src/commands/ask.ts — 删除重复实现，改为调 core/query/ask.ts（唯一数据路径）
```

**兼容性约束（对齐 v0.7.0 zero-migration 原则）**：
- `AskResultV03` 现有字段（query/matched/recommended_files/evidence_paths）保持不变，新字段只增不改；
- matched 项保留 match_type/confidence/graph_distance/file，新增 score/reasons/factors；
- MCP `pmem_ask` / `pmem_context` 出参向后兼容；
- 不改 Markdown card schema — 不需要用户迁移；
- SQLite runtime index：`rebuild` 自动创建/刷新 `card_fts` FTS5 虚拟表，纯重建产物，不属 schema migration；
- 不改卡片格式。

## 四、CLI 变化

```bash
pmem ask "<query>" [--explain] [--limit N]
pmem recall --mode brief|normal|deep [--budget N]
pmem context "<task>" --budget N     # 底层自动升级，接口不变
```

- `--explain`：输出 reasons/factors 明细（compact 时为单行注记，json 时全量）。
- `--mode brief`：只输出 L0+L3；`normal`（默认）：L0-L3 标准；`deep`：放宽 L2 数量上限。

## 五、实现分阶段

### Phase 1: Engine core（P0）
- intent.ts / candidates.ts / scoring.ts 纯函数 + 单测
- source_file 通道、FTS 常态化 bm25 加权
- ask.ts 重写为编排层；commands/ask.ts 去重

### Phase 2: Pack & modes（P0）
- pack.ts L0-L3 分层渲染 + 单测
- recall --mode、ask --explain/--limit
- context.ts 接入 engine

### Phase 3: 测试与 dogfood（P0）
- 大 fixture（≥40 卡）E2E：精确命中、模糊命中、图扩展、stale 降权、预算裁剪、确定性
- 用 pmem 自身 .pmem dogfood 验证
- README / SKILL.md 文档更新

## 六、测试计划

| 类别 | 用例 |
|---|---|
| 精确 | card ID 全等首位；文件路径命中 source_file 通道；tag 命中 |
| 模糊 | 关键词经 FTS top-3 命中；CJK 查询 |
| 融合 | 同卡多通道命中分数合并、reasons 累积 |
| 图 | 1-hop 继承分衰减；2-hop 不越界 |
| 降权 | dirty 卡降权可见；superseded ×0.5；旧卡 recency 衰减 |
| 预算 | budget=500 时 L0 完整、L2 被裁；brief/deep 模式差异 |
| 确定性 | 同查询两次输出逐字节一致 |
| 回归 | 现有 260 测试全绿；AskResultV03 出参字段不丢 |

## 七、风险

| 风险 | 缓解 |
|---|---|
| FTS 常态化引入噪音 | fts base 上限 0.8，低于所有精确通道 |
| 打分调参主观 | 权重集中在 scoring.ts 常量表 + manifest 可覆盖；用 dogfood 查询集校验 |
| 兼容性破坏 | 出参只增不改；回归测试锁定 |
| 范围蔓延到 embedding | 明确排除，见 2.3 |
