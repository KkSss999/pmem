# Memory 代码设计基线

本文将 [Memory System 决策](memory.md) 落到领域、服务和适配器边界；阶段进展与未完成能力见 [路线图](memory-roadmap.md)。内部能力不代表宿主适配或质量验证已经完成。

## 职责和依赖

- `domain/memory` 定义空间、L0 对话、访问上下文及错误，不依赖 SQLite、Drizzle、模型或入口。
- `service/memory` 校验输入、执行空间和 L0 用例，通过本领域仓储端口读写；它不决定调用方身份是否可信。
- `db/memory` 拥有 Memory 的 Drizzle 表、迁移和仓储实现；数据库连接由底层设施持有。
- `server/memory` 是内部装配入口，将同一个 Runtime 的连接交给仓储并装配 Service；数据库资源由 Runtime 关闭。
- `server/workspace` 默认将工作空间定位到 `~/.pmem`，数据库为 `pmem.sqlite`；创建、打开和显式迁移分别执行，打开不建目录或自动迁移。内部测试可以传入独立目录。
- Memory SDK、CLI、MCP 和宿主适配后置。当前通过内部装配入口使用 Memory Service，不将 DB、ORM 或行类型暴露到领域接口。

## 空间与访问

Memory 迁移创建一个稳定标识为 `personal` 的个人空间。用户决定创建的其他空间有独立标识。内部装配的调用方提供可信访问上下文：可读空间、可写空间和是否允许管理空间。Service 使用该上下文约束操作；它不认证调用方。记忆关联允许该条 L1 被关联的可读锚定空间召回，但不授予整个空间或其 L0 原文的读取权限。

创建空间、列出可读空间和锚定空间属于空间用例。锚定结果包含个人空间及调用方选定的空间；缺失或不可读的空间不能被静默加入。如何保存用户选择、获得可信身份以及 Agent 提问属于后续宿主适配。

每条 L1 未来归属一个空间，并关联多个其他空间。数据库使用关联表表达空间 ID 列表，按记忆 ID 和空间 ID 分别建立索引；L0–L1 来源关联采用独立关联表。关系属于 Memory 自有数据，不引入独立图数据库或跨领域表访问。L1 表及索引随 M2 实现，其生成、更新、遍历与排序细节在相应阶段设计和评测。

## L0 接口与存储

每条 L0 包含稳定 ID、空间 ID、单调的存储序号、`user` 或 `assistant` 角色、原始文本、PMEM 记录时间，以及宿主可提供的来源、来源事件 ID、会话 ID 和发生时间。未知信息保持缺失，正文原样保存。

- `appendL0` 接收一条消息及可信访问上下文；空间必须存在、可写且可读，因为返回结果包含持久化记录。`getL0` 按 ID 读取时将可读空间作为查询条件；`listL0` 在指定可读空间内按存储序号向前分页，可按会话过滤。
- `sourceEventId` 存在时必须同时给出 `source`。`(spaceId, source, sourceEventId)` 是来源事件的去重范围；调用方需要确保 `source` 足以区分不同来源或会话。相同标识及相同消息返回已有记录；同标识但消息字段不同返回冲突。没有事件 ID 的消息每次独立保存。
- 发生时间须为带时区的 ISO 时间；未提供时保持缺失。记录时间由 PMEM 生成。
- 写入和去重检查由同一 SQLite 事务完成。空间外键及角色约束由数据库保证；数据库或事务错误如实向调用方传播。只读模式拒绝写入。
- 新建数据库在初始化迁移时创建个人空间；已有基础数据库需要显式迁移并创建备份，打开不会自动迁移。

## 后续领域能力

L1 使用独立 Service 和 DB Adapter：调用方以稳定任务 ID 提交可访问的 L0 来源及目标空间，重复提交相同任务返回已有任务；相同 ID 对应不同输入时报告冲突。单一来源空间可自动继承，多来源空间必须指定目标。候选关联空间由调用方提供，跨空间的实际来源也可成为关联空间；每条 L1 只保存该条记忆实际关联的空间。

任务状态为 `pending`、`running`、`succeeded`、`failed` 或 `unknown`。认领任务和提交结果使用运行标识防止并发及中断后的旧执行覆盖新结果。中断标记与重试需要显式调用，结果未知时不自动重放。调用方可按空间分页查看任务；自动调度和宿主生命周期的接线仍待设计。

每批通过一次模型 API 调用生成内容、主抽象、线索、来源 ID 和关联空间 ID。Service 校验模型输出只引用本次可用的来源和空间，在事务内写入 L1 及其关联并完成任务；提交前重新检查来源与调用上下文。新 L1 的相似维护状态为 `pending`；确认状态、全文／向量索引、召回排序和相似记忆维护在 M3–M4 继续设计。

## L1 相似维护

创建 L1、建立其提炼任务结果关联和维护任务在同一数据库事务中完成；维护任务持久化 `pending`、`running`、`succeeded`、`failed` 或 `unknown`，并可按空间查询。旧数据库需要显式备份迁移，迁移为既有 L1 回填任务与结果关联；迁移本身不调用模型。

内部调度器使用具备维护判断能力的模型时，会在后台自动批量处理，每批最多 5 条记忆，与提炼任务共享单个调度器最多两个并发调用的额度。相同完整共享空间集合的维护批次互斥；该集合中有运行、失败或未知任务时，其后续维护等待显式解决，其他集合可以处理。无候选记为 `no_candidates`，不调用模型，也不表示不存在未找到的相似记忆。调用方可查询任务、显式标记中断和重试；未知结果不自动重放。只支持提炼接口的模型不会启用自动维护，调度器状态可观察该情况。宿主仍需显式启动和停止内部调度器。

维护的 SQLite 查询、索引检查和提交目前在调用进程同步执行；模型请求异步进行，但这并不保证维护对同进程 Agent 的延迟没有影响。大规模数据、跨进程竞争及调用资源预算尚未评测。

候选使用已有关键词索引，按维护任务的单调序号确定单向候选顺序；查找前检查索引，条件包含完整共享范围一致和双方归属空间可读可写。每条最多 5 个候选；词项从正文、主抽象及线索的前 2048 字符中取得，最多 32 个，可能遗漏相似记忆。同批新 L1 也可参与比较。模型一次接收一批待判断记忆与候选，仅包含 L1 ID、正文、主抽象和线索；无 L0 原文或完整空间、来源信息。模型输出 `keep`、`uncertain` 或 `merge`；只有提供的候选 ID 可用于合并，格式和数量错误会使任务失败。

合并时保留候选 L1 的 ID、归属和空间关系；新内容、抽象和线索由模型生成，双方来源以及提炼任务的结果关联在同一事务中汇集，随后删除被合并的 L1。提炼任务可指向同一条最终 L1，不保存被移除的 L1 版本。提交前重新检查双方内容、来源、空间集合、提炼任务关联与权限；发生变化时重新判断。同一批多个判断涉及已变化目标时，后续任务回到待处理。事务失败不留下部分合并；任务保留可观察的失败或未知状态，晚到的旧调用不能覆盖新任务。模型对语义的判断和候选检索质量未被结构校验保证。

模型端口位于领域边界；Other 层支持 OpenAI 和 DeepSeek 的 Chat Completions、Responses，配置和凭据由调用方传入。DeepSeek 默认模型为 `deepseek-flash`，默认地址为 `https://api.deepseek.com`；Chat 使用 JSON 输出模式，Responses 使用 JSON Schema。服务仍校验内容、来源和空间 ID，并识别拒绝、未完成和错误响应。凭据不写入仓库或数据库。

DeepSeek 的两种协议已使用合成对话进行提炼验证，结果和已发现的质量问题见 [L1 提炼质量评估](l1-quality-evaluation.md)；该验证不代表召回质量或生产环境已验收。

模型调用不放在数据库事务内。内部调度器可以自动安排和运行任务；它需要内部调用方显式启动与停止，宿主生命周期接线尚未实现，不能假设进程长期运行。默认工作空间的 SDK 接入、Knowledge 和旧数据迁移另行设计；L2 见 [L2 代码设计](memory-l2-design.md)，L3 见 [L3 关键词缓存设计](memory-l3-design.md)。

## 自动调度与召回

已确定自动提炼以持久化 L0 为起点，按来源标识、宿主会话 ID 和归属空间分组。会话身份由宿主运行时提供；PMEM 管理批次与进度，不生成另一套会话 ID。缺少可靠的来源或会话上下文时，自动采集或提炼应明确报告，不能猜测归属；现有允许可选会话字段的 L0 写入接口仍保持原状，手动写入的最终规则待讨论。来源标识需要在接入时覆盖会话 ID 的实际唯一范围，并非认证或空间授权。

内部调度器由 `server/l1-scheduler` 装配，调用方提供模型和可信访问上下文并显式启动。其 `capture` 要求来源及会话 ID，先持久化 L0，再通知后台；其他 L0 写入只要包含这两个字段，也会由调度器周期扫描发现。没有来源或会话的普通 L0 写入仍可使用，但不会进入自动提炼；自动捕获接口会明确拒绝缺少上下文的输入。

L0 插入与分组登记在同一事务中完成；每组任务、来源和已安排游标在另一个事务中一起保存。每组按序号处理不重叠的最多 10 条消息，达到 10 条或最后活动后空闲 600 秒时触发；一个调度器最多并行两个不同组，每秒扫描持久化状态。数量和空闲触发不结束会话。新迁移会登记已有的带来源及会话 ID 的 L0；显式启动调度器后，未被已有 L1 任务引用的历史 L0 也可被提炼。安排时已被任务引用的记录会跳过；独立手动提交仍可能产生重复任务。迁移不会调用模型，只有启动调度器并提供模型后才会执行提炼。

`pending` 可在重启后继续处理；`running`、`failed`、`unknown` 的任务阻塞同组后续批次，其他组仍可运行。没有自动重试策略：调用方通过已有 L1 接口显式标记中断和重试；不能仅凭进程启动就推断其他工作者已经停止。调度器 `status` 报告内部调度故障；非模型调度错误会暂停领取，修复后需显式 `resume`。`stop` 停止领取新工作并等待已启动调用结束，调用方随后才能关闭数据库。跨进程全局并发上限、超大输入预算及真实宿主启动、停止与恢复仍待设计和验证。

L1 召回采用统一内部入口：调用方提供查询、锚定空间及可信可读空间，Service 检索归属或关联到可读锚定空间的 L1，并返回记忆、可读来源 ID、来源完整性和相似维护状态。关联授权共享该 L1；L0 原文及其来源 ID 仍需原文空间的读取权限，其他记忆也不因此自动共享。索引是可重建的派生数据；索引缺失、过期或检索失败必须可观察，不能把故障伪装成无匹配。

首版内部关键词召回使用 SQLite FTS5 trigram 索引保存正文、主抽象和线索，通过数据库触发器在同一事务同步，新旧数据通过显式迁移建立索引。查询按词分段并以匹配词数排序，少于三个字符的词使用扫描。召回在一致的读取事务中检查索引定义及同步触发器、SQLite FTS 完整性以及索引与权威 L1 正文、主抽象和线索的一致性；异常返回 `INDEX_MISSING`、`INDEX_STALE`、`INDEX_CORRUPT` 或 `INDEX_UNAVAILABLE`，不伪装成无匹配。SQLite 3.44 以前缺少所需的虚拟表完整性检查能力，返回不可用。

具有空间管理权限的内部调用方可检查索引状态，并在可写数据库中显式重建：在同一事务内重建 FTS 和触发器、从权威 L1 数据填充并复查，失败时回滚。遇到占用索引名称但定义不符的未知对象时拒绝覆盖。重建不更改 L0、L1、来源及空间关联；只读打开支持检查和召回，不支持重建。当前每次召回都执行完整性和内容一致性检查，其开销随索引规模增长，规模性能尚未评测；它依赖 SQLite 的完整性检查，不能承诺检测所有硬件或数据库故障。默认不使用 Embedding；在 Memory 主体完成后再考虑可选接入和对照实验。一次统一入口不意味着保证一次查询就能找全。

批次阈值、跨批上下文、失败恢复和召回质量仍需真实工作负载评测；相似维护继续独立于首次可召回状态。

### 自动提炼：参考 TencentDB 的首版方案

TencentDB 当前代码默认每 5 轮对话或空闲 600 秒触发，支持首次以 1、2、4 轮逐步增加阈值；L1 一次从游标之后处理约 10 条 L0，额外读取用于判断积压，并在失败时有限次数重试。具体见 [配置](https://github.com/TencentCloud/TencentDB-Agent-Memory/blob/ecc01a545da0b2ac6cae2f0f0af0d39d41469793/MemoryCore/src/config.ts)、[调度器](https://github.com/TencentCloud/TencentDB-Agent-Memory/blob/ecc01a545da0b2ac6cae2f0f0af0d39d41469793/MemoryCore/src/utils/pipeline-manager.ts) 和 [L1 runner](https://github.com/TencentCloud/TencentDB-Agent-Memory/blob/ecc01a545da0b2ac6cae2f0f0af0d39d41469793/MemoryCore/src/utils/pipeline-factory.ts)。这是源码参考，并不证明这些参数适合 PMEM。

以下为 PMEM 首版方向，参数仍需评测：

- 每组待处理 L0 达到 10 条或空闲 600 秒后安排批次；按持久化序号从最早未安排消息开始，单批最多 10 条。两项数字是初始实验值，不是质量或延迟保证。保持每组串行，跨组并发上限需要通过 API 成本和限流评测确定。
- 批次不默认重叠，避免重复提炼；切分可能丢失前文，需以跨批指代、连续问答等样本评测。若结果不足，再设计有界上下文，并区分新消息、辅助上下文和可引用来源，防止仅根据旧上下文生成重复记忆。
- 条数不限制单条消息的大小；模型输入上限、超大消息处理与完整原文保存需一起设计。不能静默截断原文后把整条 L0 标记为已处理。
- 用 L0 单调序号表达批次边界，任务来源与已安排进度同事务持久化；提炼成功或合法空结果都须如实记录。成功写入记忆及任务完成状态同事务提交。重启后从持久化状态恢复，不能只依赖内存定时器。批次与消息的唯一性、并发竞争和异常退出须在实现时验证。
- 已知失败保留原因和批次，何种错误可以自动重试以及次数、间隔待定；远端结果未知、进程中断和提交结果未知不能盲目重放，应先核实本地任务状态并按恢复策略处理。首版建议同组后续批次等待该批次处理，避免越过未解决的缺口；其他组不受阻塞。现有任务的中断标记和重试仍为显式操作。

TencentDB 使用记录时间作为游标，并在源码中注明极端情况下同毫秒记录可能跨查询上限而被跳过；PMEM 使用已有的单调序号设计游标，仍需验证各分组过滤及分页边界。提案不假设宿主能始终提供会话结束事件，也不假设后台进程始终运行。
