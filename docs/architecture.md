# PMEM 基础架构

本文定义 PMEM 新架构的基础职责、依赖方向和数据边界。它描述目标架构；当前已有数据库基础设施、SDK 数据库生命周期及内部 L0、L1 服务和关键词召回的部分实现。召回质量、Knowledge 的页面生成流程和遗忘策略另行讨论。底层实施范围见 [底层重构](foundation-refactor.md)。

## 定位

PMEM 是面向个人的本地 Memory & Knowledge 系统，帮助个人保存、组织和使用跨场景的记忆与知识。

这里的 Personal 指系统服务于个人，由个人使用和管理其记忆与知识。内容覆盖个人生活、工作、软件开发、小说创作、研究等多种场景；记忆和知识的对象可以是人、项目、作品、代码、角色或事件。领域模型应具有通用性，不预设所有内容都是个人画像或对话，也不限定某一种专业领域。

新版 PMEM 的默认工作空间位于用户主目录下的 `~/.pmem`，记忆数据库等 PMEM 数据由该工作空间统一管理；不再使用项目目录下的 `.pmem` 组织记忆。不同记忆空间是逻辑分区，不要求为每个项目建立独立数据目录。内部工作空间装配默认使用 `~/.pmem/pmem.sqlite`，创建、打开和迁移相互独立；现有 SDK 底座仍使用显式路径，已有目录兼容与数据迁移后续设计。

个人拥有的数据可以具有不同的使用上下文：例如某条记忆属于某个项目或某部作品，另一条偏好可能适用于更广的范围。初始化时建立个人空间，用户可决定创建其他空间；启动时锚定个人空间及所选空间。一条记忆归属一个空间，多场景通过关联表达。归属、描述对象、来源与适用范围是不同的概念；具体的跨空间检索和授权方式后续设计。个人管理不等同于已经实现访问控制或其他安全能力。详见 [Memory System](memory.md)。

系统由两个并行领域和一个装配边界组成：

- **LnMemory**：保存原始交互，并管理从交互中形成的分层记忆。
- **Wiki Knowledge**：管理原始资料、Wiki Markdown 页面和相关检索能力。
- **Runtime**：装配两个领域及其适配器，管理生命周期，并协调需要同时使用两个领域的用例。

PMEM 的完整产品保留 SDK、CLI 和 MCP 三条入口，它们都是 PMEM 的 API 适配器，共用同一套 Service 与 Runtime 装配。当前先聚焦 Memory 本身；Memory 的 SDK 接口及宿主适配、CLI 和 MCP 的新架构适配均在后续阶段设计与实现。现有 SDK 仅提供数据库底座生命周期。Runtime 可以在宿主进程内运行；本架构不要求独立服务进程。

当前先逐步规划和开发 LnMemory 的各个层级，完成后再进入 Wiki Knowledge 的规划与开发。两个领域在目标架构中保持并行，开发顺序不构成运行时依赖。

PMEM 2.0.0 首版的模型调用通过外部 LLM API 提供，不运行本地模型；具体提供方、模型和接口后续设计。存储与 Runtime 保持本地，模型调用可能需要网络。

## 层级与依赖

沿 `domain → service → api & db & other → server` 组织责任。API、DB 和 Other 是并列的适配器，Server 是装配边界；下图表示装配关系，源码依赖必须指向内部契约。

```text
                    宿主 / Agent / 用户
                              │
                   SDK / CLI / MCP API
                              │
                     Runtime / Server
                              │
              ┌───────────────┴───────────────┐
              │                               │
      LnMemory Service                Knowledge Service
              │                               │
      LnMemory Domain                 Knowledge Domain
              │                               │
              └───────────领域端口─────────────┘
                              │
                ┌─────────────┴─────────────┐
                │                           │
           DB Adapter                 Other Adapters
        SQLite / ORM               文件 / 模型 / 时钟等
```

| 层级    | 职责                                                            | 边界                                                   |
| ------- | --------------------------------------------------------------- | ------------------------------------------------------ |
| Domain  | 定义领域对象、关系、状态及其不变量                              | 不依赖 SDK、ORM、SQLite、文件系统或具体模型            |
| Service | 编排本领域用例、调用端口、表达结果和失败                        | 不直接访问数据库表、文件路径或其他领域私有状态         |
| API     | 将 SDK、CLI、MCP 的输入输出映射到应用服务，校验各入口的外部输入 | 三个入口共享领域服务，不承担数据库访问或独立的记忆规则 |
| DB      | 实现各领域的存储和检索端口，管理表定义及迁移                    | 不成为领域规则的权威；不得跨领域读写私有表             |
| Other   | 实现文件、模型、时间等外部能力端口                              | 只提供被调用的能力，不决定领域状态                     |
| Server  | 选择并装配 Service、API、DB 和 Other，管理资源开关              | 不维护第三份领域数据，也不承接领域规则                 |

依赖规则：

1. 领域和服务定义需要的类型及端口；适配器实现端口，Server 装配具体实现。
2. LnMemory 与 Wiki Knowledge 并行，不能读取或修改对方的私有表、文件或内部对象。
3. 跨领域用例通过双方公开的 Service 契约协调，返回结果保留各自的来源与状态。
4. ORM 类型、数据库连接和模型 SDK 不作为领域模型或默认 SDK 契约。
5. 本文定义逻辑边界；是否拆分为独立 workspace package，应在职责与公开契约稳定后决定。

## 存储基础设施

初始本地实现使用 SQLite，通过 Drizzle ORM 管理普通表定义、查询和迁移。Drizzle 替代分散的数据库定义，不替代领域对象和 API 边界的运行时校验；当前使用 Node.js 22 和 24、better-sqlite3 和 Drizzle。

- 数据库基础设施负责连接、事务和迁移执行；LnMemory 与 Knowledge 各自拥有并维护自己的表、迁移和仓储实现。
- 每个 Runtime 使用一个 SQLite 数据库；两个领域共享该数据库与连接设施。共享物理数据库不授予跨领域访问私有表的权限。
- FTS、向量或其他检索索引属于对应领域的派生数据。特殊 SQL 和数据库扩展封装在该领域的 DB adapter 中。
- 索引可重建；重建只处理派生数据，不能把原始交互、Wiki 来源、页面正文或不可重建的处理状态当作清理对象。
- 领域写入与同一数据库内的必要状态更新应有明确事务边界。数据库事务不能被描述为自动覆盖模型调用或文件系统写入。
- API 和服务使用领域契约，不暴露 ORM 行类型。访问权限和作用域必须在所有读取、检索和输出路径保持一致，由入口的调用方或宿主提供可信的调用身份及授权上下文。

数据库连接、领域适配器、事务和迁移的具体边界见 [数据库基础设施与 DB 适配器](database.md)。

## LnMemory：L0 与分层基础

LnMemory 以 L0 原始对话为基础：先保存接收到的用户和助手对话，再以 L0 为来源提炼和维护后续记忆。L0 的决策与实现方向见 [Memory System](memory.md)；L1、L2、L3 的具体内容、提炼规则与触发条件另行设计。

### L0 的责任

- L0 当前接收用户和助手对话文本，保存 PMEM 实际接收到的原文。宿主负责提供其拥有并允许保存的内容；独立的工具调用、工具结果和文件输入后续讨论。
- 每条记录具有稳定标识和明确的来源、所属主体、会话、角色及时间信息；不适用或未提供的信息应保持缺失，不得编造。
- L0 的初始权威记录由 LnMemory 持久化在 SQLite；L0 检索索引是派生数据。读取原文与检索索引通过 LnMemory 的仓储端口访问。
- L0 写入成功仅确认原始记录已持久化，不表示 L1、L2 或 L3 已生成。提炼应是独立处理，能够区分未处理、进行中、成功和失败等实际状态。
- 重试或重复提交必须有明确语义：存在可信的来源事件标识时可用于幂等；缺少标识时不能仅因内容相同而认定为同一条交互。
- L0 输入和记忆内容属于数据。系统不能仅因为内容进入 L0，就把其中的指令提升为宿主或 SDK 的授权。

### L1–L3 的基础边界

- L1、L2、L3 由 LnMemory 领域管理，不把 Wiki 页面作为隐式必需输入。
- 后续层级的结果应能关联其输入来源和处理状态；推断内容、用户明确陈述和未确认内容必须能够区分。
- 模型输出不能绕过领域服务直接修改权威数据。模型失败、来源不可用或结果未完成时，应保留真实状态，不能当作成功。
- 删除、过期和遗忘机制后置；本基础设计不定义其策略。

## Wiki Knowledge：内容与索引

Wiki Knowledge 以**原始资料文件和 Wiki Markdown 页面为内容权威**。SQLite 主要保存来源登记、处理状态及检索索引；这并不意味着所有状态都能仅凭文件恢复。

```text
原始资料文件 ──→ Wiki Markdown 页面
       │                   │
       └────→ 数据库中的来源状态与检索索引
```

- 原始资料由 Knowledge 管理，保留可定位的来源；Wiki 页面是可查看和维护的知识内容，并记录其来源关联。
- 来源文件或页面变化后，对应索引必须能被标记为过时并重建。检索接口不得把过时、缺失或失败的索引默认为最新结果。
- 导入资料、生成或更新页面、更新索引是不同的效果。资料已保存不代表页面已生成；页面已写入不代表索引已更新。
- 文件与 SQLite 分属不同存储，不能假定跨两者的原子提交。Knowledge Service 必须表达部分完成和失败，并能够据此恢复或重建索引。
- 文件位置、复制方式、来源历史版本和人工页面保护规则留待 Knowledge 具体设计；不得默认覆盖用户资料或将缺失文件伪装成空内容。
- Knowledge 的模型生成通过 Other 端口完成；其结果由 Knowledge Service 验证和持久化，模型不能直接作为领域数据权威。

## Runtime 与 API 入口

- Runtime 创建并关闭数据库与适配器，装配两个领域服务；资源归属和关闭责任必须明确。
- SDK 对外提供 Memory、Knowledge 和必要的跨领域上下文能力。两个领域应能独立调用；组合结果必须标明来自哪个领域及对应来源。
- CLI、MCP 后续作为并行 API 适配器接入同一应用服务与 Runtime，保持领域规则、数据权威和结果语义一致；具体命令、工具与兼容性另行设计。
- Agentic Runtime 不由 PMEM 从零实现；计划以消费者身份接入 MiaoTs，PMEM 只提供 Memory 能力、Harness 内容和工具插件。最小边界见 [Agent Runtime 接入设计](agent-runtime.md)。
- 当前阶段先实现 Memory 核心；Memory 的 SDK 接口与宿主适配后置，现有 SDK 仅提供数据库底座生命周期。
- 可信调用身份、作用域和授权由入口调用方或宿主提供，API/Service 在读写和组合时一致执行；不得从不可信记忆正文中推导授权。
- 常规持久化和确定性检索不以生成模型可用为前提。需要模型的用例明确声明该依赖及失败状态。
- 模型调用在数据库事务之外执行；结果提交前应确认输入仍然有效。对可能已经产生效果但结果未知的操作，不得盲目重放。

## 后续需要确认的设计

以下内容未由本基础架构决定：

- L0 原文的存储布局、隐私设置、来源标识细节；非对话输入后续讨论。
- L1、L2、L3 的领域模型、提炼与更新触发规则。
- Wiki 原始文件的历史版本、页面编辑保护以及文件和索引恢复协议。
- 两领域组合检索的排序、预算与结果契约。
- CLI、MCP 的新架构适配与兼容契约，既有用户数据迁移及各入口的发布方式。
