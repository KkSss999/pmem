# Memory System 路线图

本文用于跟进 PMEM Memory 系统的设计、实现与验证。领域决策以 [Memory System](memory.md) 为准，职责与依赖方向以 [基础架构](architecture.md) 为准。阶段状态应以实际代码和验证结果更新；设计完成不代表功能已实现。

## 当前状态

| 工作                                      | 状态                                                     |
| ----------------------------------------- | -------------------------------------------------------- |
| SQLite、Drizzle 与 Runtime 数据库生命周期 | 已实现基础设施，已有针对性验证                           |
| L0 原始对话                               | 已实现内部领域、Service 和 SQLite 适配器，针对性验证通过 |
| L1 记忆、来源关联、主抽象和线索           | 内部提炼、存储及自动调度已有针对性验证；宿主接入后置     |
| L1 召回与相似记忆维护                     | 内部关键词召回、索引恢复及相似维护已有针对性验证         |
| L2、L3                                    | L2 与 L3 设计基线已确定，实现未开始                      |
| Memory SDK、宿主适配、CLI、MCP            | 后置；现有 SDK 仅提供数据库生命周期                      |

当前聚焦 Memory 自身：领域模型、服务、数据库适配器、模型调用与召回。内部设计和验证不以 Memory SDK 或宿主适配已经完成为前提。首版模型能力通过外部 LLM API 提供；不运行本地模型。

## 2.0 长线开发方式

2.0 以 1.3.6 之后的 `main` 为基线，在 `2.0-foundation` 分支推进；`main` 继续承接 1.x 发布，迁移前快照保留在 `backup/2.0-snapshot`。2.0 发布时使用 `2.0.0`，在 Memory SDK 可发布前不发布该分支。

仓库不使用 GitHub Actions。每次提交前在本地执行 `bun run check`（构建、lint、格式检查和全部测试）；失败即视为未完成。旧 1.x 的 CLI、MCP、semantic runtime 和 `.pmem` 代码不回到 2.0。

阶段按 M5 → Memory 首版收口 → M6 → SDK/宿主 → Knowledge 推进，一次只做一个阶段。每个阶段先设计后实现，新增行为必须有针对性测试；失败、中断、权限和并发状态必须可观察。不删除或重置用户数据，迁移必须单独设计和授权。

长线风险继续记录在路线图中：真实宿主生命周期、跨进程并发、真实崩溃恢复、L1 提炼准确率、召回质量和规模性能仍未建立；1.x 与 2.0 双线维护的成本也需要持续观察。

## 接下来的工作

1. **收口 L2 并实现 L3（M5）。** L2 核心、自动登记、调度、合并失效、FTS 候选和提示词适配器已实现；下一步扩展真实模型评估，然后实现 L3 关键词缓存。
2. **完成 Memory System 首版。** L0、L1 及相似维护、L2、L3 的内部能力完成并进行对应行为验证；具体层级契约和完成条件随设计确定。SDK、宿主适配与 Knowledge 继续后置。首版完成不代表整体召回准确率已达标。
3. **开展 Embedding 可选接入与召回对照实验（M6）。** 在完整的分层 Memory 基础上设计评测，比较现有召回与引入 Embedding 后的质量、延迟和成本，再决定是否接入及其方式。

M2 仍需后续评估跨批指代、超大输入、提炼准确性、真实进程中断和多进程资源竞争。这些不因内部调度实现而视为完成。Memory 的 SDK 和宿主适配继续后置；Embedding 的可选接入及其对照实验在 Memory 主体完成后进行。

## 阶段与完成条件

### M0：Memory 代码设计

**状态：代码设计基线已结束，见 [Memory 代码设计基线](memory-design.md)。**

- 已确定个人空间、启动锚定、单一归属、多空间写入，以及由记忆携带空间 ID 列表的跨空间关联；继续明确可信调用身份及跨空间遍历，确定可访问范围如何贯穿读写与召回。
- 设计 L0、L1、来源关联、后台处理状态与各层职责，明确领域端口、领域 DB 适配器和 Runtime 装配边界。
- 设计模型 API 端口和错误表达；明确后台任务的触发、宿主生命周期、恢复及关闭语义。
- 决定首版召回需要哪些索引和外部模型能力；排序和阈值以评测为依据。

M0 已确定分层、空间、L0 接口和 L1 的实现方向。L1 模型调用、后台调度、召回排序及评测等未决细节在 M2–M4 继续设计，不表示这些能力已经实现。

### M1：L0 原始对话

**状态：内部实现已完成针对性验证。依赖 M0 中的 L0 与范围契约。**

- 实现用户与助手对话正文的保存和读取，使用 LnMemory 自有的 SQLite 表与迁移。
- 保存稳定标识及宿主实际提供的来源、会话和时间信息；明确可信来源标识的幂等与冲突语义。
- 保持原文，明确写入成功、失败和结果未知的边界；写入不等待模型提炼。

完成条件：通过服务接口写入后可读回原文；重复提交、缺失信息、隔离范围和持久化失败按契约表现。

已在本机通过 10 项 L0、迁移及工作空间针对性验证，覆盖原文往返、空间隔离、来源幂等及并发、只读、迁移备份与回滚、写入失败和锁冲突恢复；真实宿主接入和其他平台未验证。

### M2：L1 提炼与来源

**状态：内部提炼、存储与自动调度已有针对性验证，系统性质量评估和宿主接入未完成。依赖 M0 的 L1 与模型契约和 M1 的 L0。**

- 一次模型调用从一批 L0 生成 L1 记忆内容、主抽象和线索；校验输出与来源关联。
- 以数据库关联保存 L0–L1 多对多来源；L1 不复制 L0 原文，记忆及必要来源关联一起提交。
- 新 L1 持久化后标记为可召回、相似关系尚未整理；内部关键词召回已接入。整理状态与确认状态分开。
- 保存提炼工作的真实状态，处理 API 失败、进程中断和恢复；不将 L0 保存成功等同于 L1 已生成。
- 自动提炼按来源标识、宿主会话 ID 和归属空间分组，PMEM 持久化批次与进度；数量和空闲触发不结束会话。[首版批次与恢复方案](memory-design.md#自动提炼参考-tencentdb-的首版方案)参考 TencentDB，内部调度已实现，参数和跨批上下文仍待评测。

完成条件：可从 L0 形成 L1，并按关联回读原文；模型失败、错误来源、重复处理和恢复行为可区分且不破坏原文。

当前已通过模拟模型、HTTP 与迁移的针对性验证，覆盖提炼、来源校验、跨空间关联、自动批次、显式恢复、失败回滚和两个调度器的竞争。真实进程崩溃及跨进程全局并发未验证。[小规模合成样本评估](l1-quality-evaluation.md)发现错误空结果及事实、来源问题，提示词已调整但准确率尚未建立。真实宿主生命周期接线及真实场景质量评估尚未完成。

### M3：L1 召回与索引恢复

**状态：内部关键词召回及索引异常检测、重建已通过针对性行为验证，质量与规模表现尚未评测。依赖 M0 的范围与召回契约，以及 M2 的 L1。**

- 建立单一内部召回服务，直接使用主抽象和线索定位 L1；不采用多轮模型引导的查询扩展。
- 在可信范围内查询，按需读取 L0 依据；索引是派生数据，可重建并能报告未完成、过时或失败。
- 检查和重建索引，验证索引故障、权限边界及重建对权威记录的影响。关键词召回质量与规模表现保持未评测状态，综合召回评测后置到 M6。

已针对性验证索引内容缺失或过期、重复、触发器缺失或变化、FTS 数据损坏、只读权限、重建及注入失败的事务回滚；重建保留 L0、L1 和来源。每次召回的完整性检查有规模成本，尚未测量。

完成条件：召回可返回 L1 与可读来源标识，必要时能获取原文；索引状态、故障与重建行为通过针对性验证。召回准确率尚需 M6 的评测。

### M4：L1 相似记忆维护

**状态：内部维护流程已实现并经过模拟模型和临时数据库针对性验证；真实模型判断质量和宿主接入尚未验证。依赖 M2 的持久化、M3 的候选检索和 M0 的任务生命周期。**

- 参考 TencentDB 的相似候选召回与批量判断，决定新增、更新、合并或保留冲突的具体规则。
- 后台维护不阻塞 Agent 当前工作；新记忆保持可召回并明确标记尚未整理。
- 主体、上下文和完整共享范围一致时可以合并互补信息并保留双方来源；跨归属空间合并需拥有双方归属空间的写权限，合并后保留其中一条的归属。不确定或冲突时保留双方。
- 首版不保留合并前的 L1 记录或历史版本；处理并发变化、失败恢复和重复执行，更新记忆、来源关联和检索投影时保留可判断的一致性。合并提交后不承诺精确恢复原先的 L1。

完成条件：可在不覆盖无关或已变化记忆的前提下完成维护；失败、冲突和未完成状态可观察，来源仍可追溯。

### M5：L2 与 L3

**状态：L2 核心 Service、SQLite 适配器、自动变更登记、调度、合并失效、FTS 候选和提示词适配器已实现并有针对性验证；L1 关联空间更新已接入；真实模型评估见 [L2 生成质量评估](l2-quality-evaluation.md)；L3 设计完成，未实现。**

L2 围绕主题、对象或持续事项聚合 L1，使用标题、摘要和灵活正文，存储在 Memory 的 SQLite 数据中。L1 与 L2 为多对多关系，每条 L2 保留当前 L1 关联与生成时的 L0 来源 ID，并按其输入记忆的共同空间范围处理共享。新增关联信息的共享范围较窄时，保留原 L2，另建较窄范围的聚合；已有依据的共享范围收窄时，立即限制可见范围并标记待更新，安全范围无法确定时暂不召回。L2 等待对应 L1 的相似维护完成，未完成或失败不阻塞其他记忆。首版按 10 条、30 秒空闲或最早变化等待 5 分钟触发；L1 变化与待处理登记同事务持久化。每批一次结构化模型调用，可产生多个 L2 结果，单条结果提交失败不影响其他结果。L2 首版代码设计已确定，见 [L2 代码设计](memory-l2-design.md)：按归属空间分组、任务状态包含 `partial`、结果逐条提交、首版仅支持新建和更新、使用 FTS5 召回；实现未开始。

L3 是从 L2 沉淀出的长期关键词缓存，不是长期文档。关键词短、间接、有代表性，保存别名、类型、基础权重、命中次数、滑动过期和来源 L2；跨空间按来源 L2 的共同范围计算可见范围，同一词在不同范围可以是不同条目，查询时按可读空间合并。L3 使用 FTS5 兜底查询，命中可提升权重；过期关键词不参与查询。首版不做深层检索、查询扩展、图遍历，也不与 Knowledge / Wiki Graph 建立任何表、API、排序或生成耦合。L3 代码设计见 [L3 关键词缓存设计](memory-l3-design.md)，实现未开始。

完成条件：L2 可从 L1 生成、更新和召回，来源与共享范围可追溯；L3 可从 L2 沉淀关键词，跨空间查询、权重和过期可观察；失败、未知和失效状态不破坏来源。

### M6：完整 Memory 召回评测与 Embedding 对照

**状态：后置到 Memory System 首版完成后。**

- 为个人、代码、创作和研究等场景建立标注样本，覆盖中文短词、专有名词、语义改写、跨会话、跨空间、冲突及无答案查询。
- 分别检查已形成记忆的召回和从 L0 到多层记忆再到召回的完整链路，区分提炼遗漏与检索遗漏。
- 对照首版召回与引入 Embedding 的效果，记录候选覆盖、前列相关性、误召回、延迟、API 成本及索引大小；根据结果决定 Embedding 是否作为可选能力接入。
