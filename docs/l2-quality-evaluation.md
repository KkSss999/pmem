# L2 生成质量：DeepSeek Flash 初步评估

2026-10-31 使用 DeepSeek Flash 和合成 L1 批次评估 L2 生成。L1 由受控的测试模型生成并完成相似维护，L2 使用真实 DeepSeek Chat Completions 和 `l2-v1` 提示词。数据库、模型输出和 API 密钥不写入仓库；评估结束后删除临时数据库。

结果只用于分析 L2 生成，不代表召回质量、真实用户数据或生产验收。

## 场景与结果

| 场景                                | 调用耗时 | Token | 结果                                       |
| ----------------------------------- | -------: | ----: | ------------------------------------------ |
| 三项项目事实聚合成一条 L2           |    2.5 s | 1,390 | 生成 1 条 L2，引用全部 3 条 L1，无额外事实 |
| 阿岚的居所与偏好初始生成            |    1.2 s |   955 | 生成 1 条 L2，引用 1 条 L1                 |
| 新增“计划搬到南城，尚未决定”        |    3.4 s | 1,527 | 更新原 L2，保留原 L1，明确保留“尚未决定”   |
| 只有寒暄的 L1                       |    1.2 s |   921 | 不生成 L2，记为 `uncovered` 并给出原因     |
| SQLite 与考虑 PostgreSQL 的冲突信息 |    2.9 s | 2,145 | 更新原 L2，保留当前 SQLite 和迁移仍待决定  |

五次调用均成功；任务状态为 `succeeded`，`promptVersion` 为 `l2-v1`。模型输出包含正确的 `action`、`l2Id`、`l1Ids` 和 `uncoveredL1Ids`。更新场景均保留了候选 L2 的现有 L1 链接。

## 发现的问题

第一次运行使用 DeepSeek Chat 的 `json_object` 模式；该模式只保证 JSON 语法，不执行 schema。模型在输出中使用了 `type`、`ownerSpaceId`，并省略了 `action`，因此 Service 正确拒绝了输出，任务失败，没有写入错误 L2。

随后在 system prompt 中加入了明确的输出形状和“必须使用 `action`，不要添加 `type`、`status`、`ownerSpaceId`”约束，并在 DeepSeek 模式之外继续使用严格 JSON Schema。第二次运行全部通过。

早期输出还出现了“以上信息来自两条个人记忆记录”之类的元叙述。提示词补充“不要说明使用了多少条记忆、信息来自记录或来源没有提到什么”后，第二次运行未再出现。该检查只基于小样本，不能证明问题消失。

## 初步观察

- 聚合：三项独立事实被合并成一条主题明确的 L2，没有明显编造
- 更新：新增信息被整合进原 L2，而不是重复新建；旧 L1 链接保留
- 不确定性：模型保留了“计划”“尚未决定”，没有把计划写成已搬迁
- 冲突：当前状态和待定迁移被同时保留，没有把 PostgreSQL 写成已采用
- 噪声：寒暄没有生成 L2，`uncovered` 原因可读
- 范围：每个结果只引用同一归属空间的 L1；跨空间权限仍由 Service 校验

## 仍需验证

- 样本很小，且 L1 由测试模型生成，不是真实用户数据
- 没有覆盖跨空间 L2、多候选 L2、长 L2 和超大输入
- 没有评测召回质量、重复率、更新准确率或人工编辑后的表现
- DeepSeek Chat 的 `json_object` 模式仍可能产生格式偏差；Service 拒绝是预期行为，但需要更多失败样本验证提示词稳定性
- 没有比较不同模型、温度、候选选择策略和提示词版本
- 没有评估真实 API 的成本、限流和网络失败分布

下一轮应扩大合成和经授权真实样本，逐条标注事实、来源、冲突、范围、更新动作和 `uncovered` 判断，并记录格式失败、空结果和网络未知的独立比例。
