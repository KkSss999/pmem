# v1.1 前置设计决策：System Memory Release

> 状态：draft → 待评审锁定
> 日期：2026-07-22
> 依据：用户架构决策（System Memory + Miao Integration + 三条红线）

## 一、定位与边界

### 核心定位

> **pmem v1.1 — System Memory Release**
>
> 将 pmem 从单项目 Memory Runtime 升级为 OS 级 System Memory Infrastructure。
> Miao 是旗舰使用者和联合验证平台，pmem 仍是独立、通用、可嵌入的开源 Memory Runtime。

### 关键边界（三条红线）

```text
第一条：pmem Core 不依赖 Miao
  Miao depends on pmem
  pmem does not depend on Miao

第二条：先定义通用 System Memory Protocol
  Miao 是第一个实现和验证者，而不是协议本身

第三条：Miao 专属逻辑全部位于 Adapter
  pmem core / pmem runtime / pmem protocol / pmem-miao adapter
  而不是 pmem core 内到处出现 miaoAgentId
```

### 正确关系

```text
Miao Agentic OS Kernel
        │
        │ Kernel Memory Adapter
        ▼
pmem System Memory Runtime
        ▲
        │ Stable Runtime API / ABI
        │
第三方 Agent Runtime、桌面软件、服务端 Agent、嵌入式 Agent
```

- Miao 是 pmem v1.1 的旗舰使用者和联合验证平台
- pmem 仍然是独立、通用、可嵌入的开源 Memory Runtime
- Miao 专属内容只存在于 adapter、policy preset 和 integration package 中
- pmem 核心不能依赖 Miao 的调度器、进程模型或通信协议

## 二、项目记忆 vs OS 级 Memory System

| 维度 | v1.0 项目记忆 | v1.1 System Memory |
|------|--------------|-------------------|
| 用户 | 一个项目目录 | 多用户、多 Agent、多应用 |
| 进程 | 随命令启动退出 | 长期运行、常驻 |
| 信任 | 调用者基本可信 | Agent 可能产生错误甚至恶意记忆 |
| 并发 | 低频率、单用户 | 多 Agent 并发读写 |
| 隔离 | 无需 | 权限隔离、namespace 隔离 |
| 容错 | 偶尔 rebuild | 崩溃恢复、索引重建、优雅降级 |
| 资源 | 无限制 | 配额、背压、优先级 |
| 数据量 | 有限（百张卡片） | 可能非常大 |
| 延迟 | 不敏感 | 热路径 P95 < 10ms |

v1.1 的关键词：

> **Isolation、Capability、Reliability、Latency、Resource Governance**

## 三、安全模型

### 3.1 Memory Namespace 隔离

```text
system
user
application
workspace
agent
task
session
private
shared
```

每条记忆的完整身份：

```ts
type MemoryAddress = {
  tenantId: string;
  userId?: string;
  appId: string;
  agentId?: string;
  workspaceId?: string;
  sessionId?: string;
  memoryId: string;
};
```

默认可见性原则：

```text
Agent 私有记忆：默认不可见
应用共享记忆：显式授权
用户长期记忆：需要用户级权限
系统记忆：普通 Agent 只读或完全不可见
跨应用记忆：默认禁止
```

### 3.2 Capability-Based Access Control

细粒度 capability：

```text
memory.read
memory.search
memory.observe
memory.propose
memory.commit
memory.amend
memory.supersede
memory.forget
memory.purge
memory.share
memory.export
memory.admin
```

Capability 带约束：

```ts
{
  capability: "memory.read",
  scope: "project:pmem",
  types: ["decision", "module"],
  expiresAt: "...",
  maxResults: 20
}
```

典型分配：

- 普通 Agent：`observe` + `search`，不能直接 `commit` semantic memory
- 规划 Agent：可读项目决策，不能读取用户隐私
- 系统维护 Agent：可处理过期记忆，不能导出原文
- 用户界面：可批准记忆，不必拥有数据库管理权

### 3.3 Trust Model

信任级别：

```text
system_trusted
user_confirmed
application_trusted
agent_generated
tool_observed
imported_external
untrusted_content
```

召回结果结构：

```ts
{
  content,
  trustLevel,
  provenance,
  permissions,
  confidence,
  createdBy,
  verifiedBy,
  evidence,
}
```

Agent Runtime 由此可知：
- 哪些内容可以直接用于决策
- 哪些只是历史记录
- 哪些可能包含 prompt injection
- 哪些需要重新验证
- 哪些不能传给外部模型

### 3.4 Memory Poisoning 防护

写入链路：

```text
Observation
  → source classification
  → policy evaluation
  → injection / secret scan
  → deduplication
  → proposed memory
  → confirmation or trusted commit
```

必须防止：
- 外部网页直接变成长期事实
- 一次模型幻觉覆盖稳定决策
- 恶意工具输出植入行为指令
- 低权限 Agent 写入系统级 scope
- 一条污染记忆通过 distill 扩散到稳定记忆

### 3.5 Secret 与隐私治理

敏感度分级：

```text
sensitivity:
  public
  internal
  personal
  confidential
  secret
```

必须支持：
- 写入前 secret detection
- 字段级加密
- scope 级密钥
- 导出脱敏
- 日志不输出正文
- 用户可查看和删除自己的长期记忆
- 外部模型调用前做数据出境策略检查

## 四、性能架构

### 4.1 常驻服务

```text
Miao Kernel
├── Scheduler
├── Capability Manager
├── Tool Runtime
├── Event Bus
└── Memory Service
      └── pmem runtime
```

pmem 作为常驻服务或进程内核心模块运行。不要让每次 Agent 调用都启动 Node、解析 manifest、重建 graph、重新打开数据库。

### 4.2 热路径 vs 冷路径

**热路径**（Agent 每轮都可能执行）：

```text
working memory read
recent events
semantic recall
permission check
context packing
```

**冷路径**（后台/延后处理）：

```text
embedding generation
large-scale distillation
full graph rebuild
compaction
historical cleanup
cross-device synchronization
```

异步写入管线：

```text
写入 Observation
   │
   ├── 立即写入 event log
   ├── 更新轻量索引
   └── 投递异步任务
          ├── embedding
          ├── graph inference
          ├── distillation
          └── compaction
```

Agent 不应该等待完整蒸馏完成才能继续运行。

### 4.3 系统级 SLO

| 操作 | 目标 |
|------|------|
| Working memory read P95 | < 5 ms |
| Exact memory get P95 | < 10 ms |
| Warm lexical recall P95 | < 30 ms |
| Hybrid recall P95 | < 100 ms |
| Observation append P95 | < 10 ms |
| Policy evaluation P95 | < 20 ms |
| 空闲基础内存 | < 30–50 MB |
| 无向量组件基础安装体积 | 尽量 < 20–30 MB |

> 数值需要 benchmark 校准。没有 SLO 就容易逐渐变成一个越来越重的"知识平台"。

### 4.4 资源配额和背压

```text
max memories per namespace
max bytes per agent
max writes per minute
max recall budget
max graph expansion
max concurrent queries
max embedding queue size
```

超限行为（不能把系统拖死）：
- 降低召回深度
- 丢弃低价值 working events
- 合并重复观察
- 暂停低优先级 embedding
- 对写入方施加 backpressure
- 返回明确的资源限制错误

## 五、包拆分：Small Core, Optional Capabilities

```text
pmem-core          — 基础模型、生命周期、权限、查询接口
pmem-sqlite        — 默认本地存储
pmem-fts           — FTS5/BM25
pmem-graph         — 轻量关系扩展
pmem-vector        — 可选向量检索接口
pmem-embedding-local — 可选本地模型
pmem-sync          — 可选跨设备同步
pmem-mcp           — MCP 适配
pmem-miao          — Miao 深度适配
```

默认安装不能包含：
- 大型 embedding 模型
- GPU 运行时
- Qdrant
- 浏览器组件
- 云端同步服务
- Miao 本身

第三方开发者可以只使用 `pmem-core + pmem-sqlite`，而 Miao 可以选择完整能力。

## 六、语言与运行时路线

### 当前状态

TypeScript 非常适合 CLI、SDK、快速迭代、Agent 框架生态、MCP、开发者体验。

### OS 级需求

常驻内存、启动时间、二进制部署、可预测延迟、崩溃隔离、FFI、ARM/x86、嵌入式运行。

### 渐进式路线

```text
v1.0
  TypeScript Core API 稳定化
  SQLite runtime
  SDK / daemon / JSON-RPC

v1.1
  定义语言无关 Memory Protocol
  Rust system runtime prototype
  Miao adapter 使用 Rust runtime
  TypeScript SDK 作为客户端

v1.2+
  根据 benchmark 决定是否迁移更多核心
```

### 最终形态

```text
pmemd              — Rust 编写的轻量常驻服务
@pmem/sdk          — TypeScript Client
pmem-python        — Python Client
pmem-rs            — Rust native API
pmem CLI           — 通过本地 IPC 调用 pmemd
```

关键不是"Rust 比 TypeScript 高级"，而是 Miao 的系统层本身是 Rust 导向，使用同一种系统语言可以减少 Node 运行时依赖、双运行时内存、IPC 次数、安装复杂度和 ARM/x86 交付问题。

## 七、可靠性与崩溃恢复

### 7.1 Append-only Event Log

高频写入首先落到 append-only log：

```text
observe
commit
supersede
forget
policy_decision
permission_change
```

所有状态都能从事件回放恢复。

### 7.2 WAL 与原子事务

SQLite 配置：
- WAL mode
- busy timeout
- bounded transaction
- fsync 策略
- crash recovery test
- schema migration transaction

### 7.3 索引永远可重建

以下都不能成为唯一事实源：

```text
FTS 索引
vector index
graph cache
rank features
context cache
```

它们损坏后应能独立重建，不影响原始事件和稳定记忆。

### 7.4 优雅降级

```text
vector provider 故障 → fallback to exact + FTS + graph
graph index 不可用 → fallback to lexical recall
durable store 暂时忙 → 写入进入 bounded journal → 稍后提交
```

Memory Service 的单个增强组件不能成为整个 OS 的单点故障。

## 八、多 Agent 并发

### 8.1 原生支持

```text
Agent A private working memory
Agent B private working memory
Shared project semantic memory
Explicit shared task memory
System-global policy memory
```

### 8.2 写冲突

不能 last-write-wins 静默覆盖。应该生成冲突：

```text
memory.conflict
├── existing version
├── proposed version
├── sources
├── confidence
└── resolution status
```

### 8.3 分支式记忆

Agent 可以在自己的工作分支上形成假设：

```text
main memory
  ├── Agent A branch
  └── Agent B branch
```

只有合并或确认后才进入共享稳定层。

### 8.4 Shared Blackboard

多 Agent 协作的短期共享黑板：

```text
task.shared
  current plan
  assigned subtasks
  blockers
  intermediate outputs
```

不自动进入长期语义记忆。

## 九、Miao 集成边界

### 独立包

```text
integrations/miao/
├── adapter
├── capability-map
├── event-bridge
├── policy-preset
├── context-provider
└── lifecycle-hooks
```

### 职责划分

| Miao 负责 | pmem 负责 |
|-----------|-----------|
| Agent 身份 | 记忆存储 |
| process/task 调度 | 记忆生命周期 |
| capability token 签发 | recall |
| 用户审批 | context packing |
| 工具调用 | provenance |
| 应用沙箱 | stale/supersede |
| 系统事件 | namespace 隔离 |
| | 审计记录 |

### 稳定接口

```ts
interface SystemMemory {
  observe(input: Observation, auth: CapabilityToken): Promise<Receipt>;
  recall(query: RecallRequest, auth: CapabilityToken): Promise<ContextPack>;
  propose(input: MemoryProposal, auth: CapabilityToken): Promise<Proposal>;
  commit(proposalId: string, auth: CapabilityToken): Promise<MemoryRecord>;
  forget(memoryId: string, auth: CapabilityToken): Promise<Tombstone>;
}
```

不要让 pmem 直接调用 Miao Scheduler，也不要让 Miao 直接操作 pmem 数据库。

### Miao 概念映射到通用概念

| Miao 概念 | pmem 通用概念 |
|-----------|--------------|
| Miao Agent ID | principal / agent namespace |
| Miao Approval | memory proposal approval |
| Miao Process | task/session scope |
| Miao Capability | memory capability token |
| Miao Event Bus | observation event source |
| Miao Sandbox | namespace isolation boundary |

如果一个功能只能用"Miao 专属字段"表达，就应该停下来重新设计。

## 十、第三方兼容性保证

### 10.1 协议先于 Miao Adapter

先定义通用的 `Pmem Runtime Protocol`，再让 Miao 实现它。而不是先写 Miao 专属 API，再尝试泛化。

### 10.2 官方适配矩阵

v1.1 最少验证：
- Miao
- TypeScript 自研 Agent
- Python Agent
- MCP Agent
- 普通 CLI 项目记忆

### 10.3 Conformance Suite

第三方 provider 和 adapter 运行统一测试：

```text
storage conformance
runtime protocol conformance
permission conformance
lifecycle conformance
crash recovery conformance
```

## 十一、交付内容

v1.1 作为一个完整版本，一次性交付以下全部：

- **System Security Model**：principal identity、namespace isolation（9 级）、capability-based permission（12 种）、trust label（7 级）、sensitivity label（5 级）、audit event、secret scanning、memory poisoning defense
- **System Runtime**：常驻 `pmemd`（Rust prototype）、Unix Socket / named pipe IPC、async write pipeline（热路径同步 + 冷路径异步）、backpressure + quota + priority queue、graceful degradation（向量故障 → FTS+graph；graph 故障 → lexical）
- **Reliability**：append-only event log（所有状态可回放恢复）、WAL mode + atomic transactions + crash recovery tests、索引永远可重建（FTS/vector/graph/rank features/context cache 都不是唯一事实源）、corruption injection tests + power-loss simulation
- **Multi-Agent Memory**：private/shared scope 原生支持、branch memory（Agent 工作分支 → merge → 共享稳定层）、conflict detection（不 last-write-wins 静默覆盖）、shared task blackboard（不自动进入长期语义记忆）、per-Agent quotas
- **Miao Integration**：独立 `integrations/miao/` 包（adapter / capability-map / event-bridge / policy-preset / context-provider / lifecycle-hooks）、Miao 概念全部映射到通用概念、capability mapping + approval workflow
- **Third-Party Compatibility**：language-neutral Pmem Runtime Protocol、TypeScript / Rust / Python clients、MCP adapter、conformance suite（storage / protocol / permission / lifecycle / crash recovery）、standalone integration sample（不含 Miao 组件的 Python Agent 完整接入）

## 十二、验收场景

### 场景一：多 Agent 隔离

- Agent A 和 Agent B 同时运行
- A 无法读取 B 的私有记忆
- 两者可以读取共享项目事实
- capability 撤销后立即失效

### 场景二：记忆污染防护

- Agent 读取包含恶意指令的网页
- 内容可进入 observation
- 不能直接成为系统级长期指令
- recall 返回明确的 untrusted 标记

### 场景三：资源攻击

- 一个 Agent 每秒写入大量事件
- 触发 quota 和 backpressure
- 其他 Agent 的 recall 延迟不受明显影响

### 场景四：突然崩溃

- 写入过程中强制终止
- 重启后没有半条记忆
- event log 可恢复
- 索引可重建

### 场景五：降级运行

- vector provider 故障
- pmem 自动回退 FTS + graph
- Miao 仍能继续工作

### 场景六：第三方接入

- 一个不使用 Miao 的 Python Agent
- 通过标准协议接入
- 能完成 observe、recall、supersede、forget
- 不需要导入任何 Miao 组件

## 十三、与 v1.0 的关系

v1.0 是 v1.1 的前提：

- v1.0 冻结通用 Memory Model、Runtime API、namespace/scope、Policy Engine
- v1.1 在 v1.0 基础上增加 OS 级能力：常驻、并发、隔离、配额、崩溃恢复
- v1.1 不破坏 v1.0 的 CLI 兼容性和 Markdown 原则

```text
v1.0 Agentic Memory Runtime
  → 单项目 Memory Runtime
  → TypeScript Core API
  → CLI / MCP / SDK 统一
  → working / episodic / semantic memory

v1.1 System Memory Release
  → OS 级 Memory Infrastructure
  → 多 Agent / 多用户 / 多应用
  → 安全模型 + 性能 SLO + 崩溃恢复
  → Miao 深度集成（通过独立 adapter）
```

---

## 十四、最终建议

v1.1 可以深度服务 Miao，但遵守三条红线：

1. **pmem Core 不依赖 Miao** — `Miao depends on pmem`，反过来不行
2. **先定义通用 System Memory Protocol** — Miao 是第一个实现和验证者，不是协议本身
3. **Miao 专属逻辑全部位于 Adapter** — `pmem-miao` 独立包，核心零侵入

最终产品关系：

> **Miao 为 Agent 提供执行、调度、安全和系统能力；pmem 为 Agent 提供可治理、可恢复、可隔离的长期认知。**

这会让 pmem v1.1 不只是"为 Miao 做适配"，而是借助 Miao 这个真实 Agentic OS，完成从 **Agent Memory Runtime** 到 **System-grade Agent Memory Infrastructure** 的升级。
