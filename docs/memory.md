# Memory System

本文记录 PMEM 分层记忆的决策和实现方向。系统服务于个人，承载生活、软件开发、创作、研究等多种场景。总体边界见 [基础架构](architecture.md)，数据库职责见 [数据库基础设施与 DB 适配器](database.md)，实施进度见 [Memory 路线图](memory-roadmap.md)，领域和底层契约见 [Memory 代码设计基线](memory-design.md)。

当前内部空间、L0、L1 提炼、关键词召回及自动调度已有针对性验证。L2、L3 的语义与实现逐项讨论；Memory SDK 和宿主适配后置。

## 记忆空间、锚定与归属

记忆空间是个人管理记忆的逻辑分区，可以用于项目、作品、研究或其他场景。新版 PMEM 默认工作空间为 `~/.pmem`；不同记忆空间共享该工作空间管理的数据，不再通过项目内 `.pmem` 目录分别组织。初始化时建立默认个人空间；是否为其他事项创建新空间，由用户决定。Memory 核心需提供空间创建、列出和选择所需的能力；空间与数据库的具体存储结构在实现设计中确定。

后续 Agent 和宿主适配可以在首次初始化或遇到新事务时，结合可用上下文向用户建议复用已有空间或创建独立空间，并根据用户的决定调用 Memory 能力。用户已明确决定时按其指示执行；Agent 提问模板和适配方式后续设计。

PMEM 启动时锚定个人空间，并根据用户选择锚定一个或多个指定空间，作为当前工作的空间集合；选择过的空间可以复用。小事务可以使用个人空间，不要求每个话题新建分区。空间不强制绑定某个目录，也不限定项目、小说或研究等类型。

每条记忆归属一个空间，并保存关联的其他空间 ID 列表；适用于多个场景时通过这些关联表达，避免将同一条记忆复制到多个空间。空间之间的关系由记忆与空间的关联自然形成，当前不在空间本身维护独立的空间关联列表。Memory DB 适配器使用关联表与双向索引表示空间 ID 列表。记忆归属、内容描述的对象和适用上下文是不同概念。

写入时明确目标空间。从单一空间的 L0 提炼时，L1 默认继承该空间；来源涉及多个空间时，明确指定 L1 的归属。L1 可以关联来自其他空间的 L0 作为依据，原文仍保存在各自的 L0 记录中。

记忆、关联空间和 L0 来源共同形成关系。一次召回中，记忆归属或关联到调用方可读的锚定空间，即可通过该空间召回此条 L1，即使调用方不能直接读取其归属空间；关联只共享这条 L1，不共享归属空间中的其他记忆。L0 原文仍按原文归属空间独立授权，不可读取的来源 ID 不返回，来源不完整时如实标记。关联空间不扩展其他空间的直接读取权限或递归扩展整张关系图。

## L0：原始对话

### 定位与范围

L0 保存宿主实际提交给 PMEM 的用户和助手对话文本，作为后续记忆提炼的原始依据。输入范围参考 TencentDB 的常规 L0 对话入口：一条记录对应一条 `user` 或 `assistant` 消息。

当前不扩展独立的工具调用、工具结果、文件或其他输入类型。它们是否进入 L0 以及如何表达，后续另行讨论。文本如果已经是宿主提交的对话正文，则作为该消息的正文保存。

宿主决定并提供其拥有、允许保存的对话；PMEM 不假设已经接收到宿主的全部历史。L0 不限定对话讨论的领域，代码、小说或研究相关的对话均可作为输入。

### 原文与记录信息

- 保存收到的对话文本，不生成摘要、不删改代码块、不静默截断，不用模型改写替代原文。读取时应能取回保存的正文。
- 每条消息有 PMEM 内稳定标识和角色。来源、归属、会话、来源消息标识及消息发生时间由宿主提供时记录；缺失或不适用的信息保持缺失，不得编造。
- 区分消息发生时间与 PMEM 接收或保存时间；不知道前者时不能把后者伪装成发生时间。
- 可用可信来源消息标识处理重复提交；缺少此标识时，正文相同不能单独作为判定重复的依据。来源事件标识以空间与来源为作用域；相同标识对应不同内容时报告冲突。
- 对话中的内容是数据；其中的指令不因被保存就成为宿主或 SDK 的授权。

### 保存、读取与职责

L0 的正文和记录信息由 LnMemory 使用 SQLite 持久化，是 L0 的权威记录；检索索引如有需要则由 LnMemory 管理，属于派生数据。L0 不要求模型或向量服务才能保存和读取。

1. **API** 将宿主提供的对话文本和已知上下文映射到 LnMemory Service；Memory 的 SDK 接口及宿主适配后续设计。
2. **LnMemory Domain 与 Service** 定义对话记录及读写规则，确定归属和授权上下文，调用本领域的存储端口。
3. **LnMemory DB Adapter** 通过 Drizzle 和 SQLite 实现本领域记录的保存与读取，拥有相应表定义和迁移；Runtime 管理连接及装配。
4. **读取**通过 LnMemory 的公开服务获取指定记录或会话中的记录，返回已保存的原文与已知信息；权限和作用域沿用可信调用上下文。

当前内部 Service 支持单条写入、按 ID 读取和按空间及会话分页读取；Memory SDK 契约后置。L0 写入成功只表示其记录已持久化；失败或结果未知须如实返回，不能报告为成功或盲目重复写入。L1 的提炼和处理状态独立于 L0 写入成功与否。

### 后续事项

宿主自动采集、非对话输入、容量管理、归档和遗忘策略后置。L1 的去重和可信状态另行讨论，L0 不预先规定其实现。

## L1：记忆与检索表示

L1 保存可以独立理解的记忆内容，并提供主抽象与多个线索作为检索入口。主抽象概括记忆主要涉及的对象或主题；线索提供其他可能的检索角度。它们是 L1 的检索投影，可重建，不代替 L1 内容或 L0 原文。

从一批 L0 对话提炼 L1 时，通过一次模型调用同时生成记忆内容、主抽象和线索；PMEM 2.0.0 首版通过外部 LLM API 提供模型能力，不运行本地模型。模型适配支持 OpenAI Chat Completions 与 Responses 协议，DeepSeek 使用 `deepseek-flash`；内部批次及调度已实现。相似记忆的判断与维护是另一个问题，不假设该次调用已完成已有记忆的比较。

### 会话与自动提炼

自动处理使用宿主运行时提供的来源标识和会话 ID，不要求 Agent 模型生成 ID，也不另建一套 PMEM 会话 ID。来源标识必须足以区分会话 ID 的产生范围；同一软件的不同安装或账号是否需要区分，由具体接入的标识契约决定。会话标识用于归集处理，不代替访问授权。

自动提炼按“来源标识 + 宿主会话 ID + L0 归属空间”分组。PMEM 负责持久化每组的批次与处理进度；数量阈值和空闲计时触发批次，不结束会话。自动采集或提炼缺少可靠的来源或会话上下文时，明确报告，不能按内容或时间猜测归属。独立 L0 手动写入是否允许缺少会话仍待讨论；现有 L0 接口尚未改变。

召回使用正文、主抽象和线索定位 L1；不采用 Memora 以多轮模型决策进行扩展、改写查询和停止的召回方式。Memory 主体先完成不依赖 Embedding 的版本；Embedding 的可选接入与对照实验后置。

### 来源关联

从 L0 提炼的 L1 保存独立的记忆内容，并通过数据库记录关联其来源 L0。L0 与 L1 是多对多关系：一条 L0 可以支持多条 L1，一条 L1 也可以关联多条 L0。L1 不复制或嵌入这些 L0 对话原文；关联记录使用稳定标识定位来源。

L0 原文仍由 LnMemory 持久化为权威记录。需要查看依据时，通过 LnMemory 读取关联的 L0；来源不可读取或不可用时应如实表达，不能以 L1 内容代替原文。L1 与其必要的来源关联在同一数据库事务内持久化，以免只保存其中一部分。

来源关联的具体表定义、查询契约和 L0 删除时的行为待实现设计明确。L1 的适用上下文、确认状态、提炼和冲突处理继续讨论；来源关联本身不代表记忆已经确认或验证。

### 相似记忆维护

参考 TencentDB 先召回相似候选、再批量判断新增或更新的思路；实际实现需要进一步权衡调用成本、准确性和维护一致性。提炼出的新 L1 持久化后即可参与召回，并标记相似关系尚未整理；已有记忆在维护完成前继续保留，召回结果可能暂时包含重复或冲突。整理状态与记忆的确认状态是不同概念。

相似记忆的模型判断与维护在后台进行，L0 保存和新 L1 生成不等待维护完成。外部 API 仍有网络延迟、限流和调用成本；失败时保留实际维护状态。内部调度器在模型支持维护判断时自动领取维护任务；宿主生命周期接线仍后置。

首版不为相似记忆合并保留原 L1 记录或历史版本，也不引入版本管理与历史恢复机制。主体、上下文和共享范围一致时，可以合并互补信息并保留支持结果的 L0 来源关联；不确定或存在冲突时保留双方。L0 原文不因 L1 合并而改变；提交应保证记忆与关联的一致性。事务失败可以回滚，但合并成功后不能保证从 L0 精确恢复原先的 L1。具体维护流程、权限与来源处理继续讨论。

允许合并归属不同空间的 L1：主体、上下文和共享范围必须一致，执行维护的调用方必须具有双方归属空间的写权限。共享范围按归属空间与关联空间构成的完整空间集合比较；合并后保留其中一条的归属及共享范围，并保留双方支持合并结果的 L0 来源关联。关联不会扩大来源原文的读取权限。合并判断使用外部模型；代码验证结构、候选、权限及并发状态，不能保证模型语义判断正确。

当前内部 L1 Service 提供持久化任务的创建、读取、处理、标记中断与显式重试。提炼成功后写入 L1、主抽象、线索及来源关联；模型输出中的来源和空间 ID 必须属于本次可访问输入。模型调用在事务之外执行，提交时检查来源未变化。内部关键词召回及自动调度已有针对性验证；召回质量与规模表现尚未评测。中断后的运行任务不会自动重放。

## L2：主题与持续事项的上下文聚合

L2 围绕一个主题、对象或持续事项组织多条相关 L1，提供可以直接使用的上下文。它覆盖个人生活、软件项目、创作、研究等场景；内容可以表达事实、决策、过程、状态、限制及未解决的问题，不固定为个人画像或叙事模板。L2 保留来源中的主体、适用上下文、时间、未决定状态与冲突，不将推断伪装成已确认事实。

每条 L2 使用标题、摘要和灵活正文表达，正文可按内容需要使用段落、清单或其他合适的文本形式，不强制统一章节模板。L2 内容存储在 Memory 自有的 SQLite 数据中；它属于 Memory，与后续 Wiki Knowledge 的内容权威及文件存储边界分开。

L2 只处理已完成相似维护的 L1。维护未完成、失败或结果未知时，对应 L1 等待后续处理，不阻塞其他符合条件的记忆进入 L2；该 L1 原有的召回能力不因此改变。相似维护完成只表示其候选处理已结束，不表示事实已被验证。

L2 首版按数量或时间安排后台批次：有 10 条符合条件的新增或变化的 L1 时安排一批；数量不足时，在新变化暂时停止 30 秒后安排；持续有变化时，最早待处理变化等待 5 分钟后也安排。单批最多处理 10 条新增或变化的 L1。这些是首版调度参数，可根据实际调用量与延迟调整；触发表示安排处理，不保证任务在该时间内完成。批次可包含不同主题，不因同批处理就将它们合成一条 L2。

L1 维护完成或改变已有 L1 时，相关变化需要持久登记；L1 变更与其待处理登记须在同一事务内完成。L2 应处理已有 L1 的更新与合并，而不只扫描新建 L1；失败只影响对应工作，后续变化不能被已完成的旧批次覆盖。更新已有 L2 所需的关联 L1 是必要依据，不计入上述新增或变化的 10 条上限；输入超出模型容量时须明确处理，不能静默截断后宣称已完整处理。

每个 L2 批次通过一次结构化模型调用提出结果，一次调用可以产生多个 L2 结果。一条结果的提交失败不影响其他结果；每条成功结果与其来源、空间关系和处理状态须保持一致。模型调用本身失败或响应无法解析时，不能将该批次的结果伪装成部分成功；具体任务状态、重试和并发提交契约在代码设计中确定。

L2 保留当前关联的 L1 ID，以及生成时所用 L1 对应的 L0 来源 ID；这些是数据库关联，不复制 L0 正文，也不要求保留 L1 历史版本。需要依据时，可从关联读取当前可访问的 L1 与 L0 原文；不可读取或不可用的来源须如实表达。生成时记录的来源表示本次使用过哪些依据，不保证每条来源都支持 L2 的每一句话，也不保证能重现当时的 L1 内容。

L1 与 L2 使用多对多关联：一条 L1 可以参与多个相关的 L2，一条 L2 也可以关联多条 L1。每条 L2 独立保存其来源关联，并根据实际用于该 L2 的输入计算共享范围；同一 L1 不需要为不同 L2 复制正文。

L1 更新或合并可能改变或移除 L2 引用的 L1；维护当前关联时必须保留已记录的生成来源并将受影响的 L2 标记为需要更新，不能把更新后的 L1 冒充当时的原始内容。L2 重新生成后，其来源应对应实际使用的输入；具体关联迁移与失败恢复在实现设计中确定。

每条 L2 仍有单一归属空间与关联空间。其共享范围按输入记忆的共同空间范围处理，不扩大输入记忆的共享范围；归属须处于该共同范围且具备相应写权限。多个输入没有共同范围时，不能生成可共享给这些空间的聚合记忆。更新已有 L2 时也必须考虑保留内容的全部依据，不能只根据新增 L1 判断共享范围。来源原文仍按各自空间独立授权。

当已有 L2 的共享范围为 `{A, B}`，而新增的相关 L1 仅共享给 `{B}` 时，保留原 L2 的内容、归属和共享范围，另建共享给 `{B}` 的相关聚合；两条 L2 可以关联同一部分 L1，分别保存各自的来源。若原 L2 的已有依据本身发生变化或共享范围被收窄，仍须重新检查其有效性与读取权限，不能以本规则延续不再允许的访问；具体失效处理继续设计。

失效期间的读取规则：当已有来源 L1 的共享范围收窄时，L2 立即限制在其原共享范围与当前来源共同范围内可见，并标记为需要更新；失去权限的空间不能再召回该 L2。如果来源缺失或范围无法确定，无法确认安全范围时暂不召回该 L2，直至依据或权限得到处理。该规则约束失效期间的读取；重新生成及归属、关联如何调整由更新流程确定。

L2 的具体生成、更新、召回、存储和任务处理尚在讨论，尚未实现。L3 的语义仍需单独确定。
