# 数据库基础设施与 DB 适配器

本文记录 PMEM 底层数据库的架构决定，细化 [基础架构](architecture.md) 的存储边界。它描述目标架构；当前实现数据库连接、基础迁移与 SDK 生命周期。Memory 和 Knowledge 的具体数据模型、表结构及处理流程另行设计。SDK 契约见 [底层重构](foundation-refactor.md)。

## 定位

每个 PMEM Runtime 使用一个本地 SQLite 数据库。LnMemory 和 Wiki Knowledge 共享该数据库与连接设施，各自拥有 DB 适配器、表、索引和迁移。Runtime 负责装配并管理资源；数据库基础设施与领域 DB 适配器是不同的责任。

```text
Runtime / Server
  ├── SQLite 基础设施：连接、事务设施、迁移执行
  ├── LnMemory Service → LnMemory 存储端口 → LnMemory DB Adapter
  └── Knowledge Service → Knowledge 存储端口 → Knowledge DB Adapter
```

图中箭头表示使用和装配关系。Service 依赖自身定义的端口，DB Adapter 实现端口；只有 Runtime/Server 选择并组合具体实现。

## 数据库基础设施

数据库基础设施负责：

- 打开和关闭 SQLite 连接，应用约定的连接配置。
- 提供数据库事务设施，并向适配器报告数据库错误。
- 按确定的顺序执行已登记的迁移，检查数据库版本及迁移状态。
- 支持明确区分创建、打开已有数据库、迁移和只读打开。

Runtime 显式创建、持有并关闭自己使用的数据库资源。不能用进程级隐式数据库单例代替资源归属。多个 Runtime 可以由宿主指定各自的数据位置；同一路径被多个实例访问时，必须正确处理 SQLite 锁和繁忙错误，不能假定它们拥有相互独立的数据。

只读打开不创建数据库、不建表、不修改配置或执行迁移。运行环境无法满足只读打开时，应报告失败，不得静默切换为可写模式。

## 领域 DB 适配器

LnMemory 和 Knowledge 各自的 DB 适配器负责：

- 定义和维护本领域的普通表、索引及迁移。
- 实现本领域 Service 所需的存储与查询端口。
- 在领域对象与数据库记录之间映射，并在约定的数据库边界内完成原子写入。
- 将数据库故障、索引不可用及其他无法完成的效果如实返回调用方。

两个适配器共享物理 SQLite 数据库，但不直接读写对方的私有表。领域需要另一领域的信息时，通过该领域公开的 Service 契约访问。SQLite 本身不会根据源码目录自动实施这项隔离；公开边界、依赖约束及其验证需要在实现时落实。

数据库基础设施不定义记忆内容或知识规则。DB 适配器不决定记忆应如何提炼、合并或排序，也不成为 Wiki 原始文件和 Markdown 页面的内容权威。

## ORM 与索引

普通表定义、查询和迁移采用 Drizzle ORM；当前使用 Drizzle ORM 0.45.4 与 better-sqlite3；开发使用 Drizzle Kit 0.31.8。ORM、驱动、数据库连接及其行类型留在 DB 层，领域模型和 SDK 契约不依赖这些实现类型。外部输入仍需由 API 和领域边界校验。

FTS5、向量及其他特殊索引属于相应领域的派生数据。需要的数据库专用 SQL、扩展或自定义迁移封装在拥有该索引的 DB 适配器中。索引的建立、更新、删除与重建必须和权威数据的变化保持可判断的一致性；索引不可用或过时不能被报告为最新结果。

对当前已确定的内容权威：

- LnMemory 的 L0 原始交互由 LnMemory 持久化在 SQLite；其检索索引是派生数据。
- Knowledge 的原始资料文件与 Wiki Markdown 页面是内容权威；数据库保存来源登记、处理状态和检索索引。
- 处理状态不一定能仅凭文件恢复；重建索引不能清除不可重建状态，也不能覆盖权威内容。

## 事务边界

Service 决定用例需要达成的结果；DB 适配器在端口约定的范围内执行数据库事务。单领域操作若要求记录及其必要状态一起写入，可由该领域端口定义为一个原子操作，由其 DB 适配器完成，不需要预先建立全局通用事务框架。

- 数据库事务只保证其实际包含的数据库操作；不覆盖文件写入、模型调用或其他外部效果。
- 不在数据库事务中等待模型调用或用户输入。提交处理结果前应检查输入是否仍有效。
- 跨领域用例默认通过 Service 协调各自操作，并如实报告部分完成或失败；只有出现明确的跨领域原子需求后，才设计相应契约。
- 锁冲突、提交失败和结果未知必须可区分。只有确认未产生效果时才可安全重试；结果未知时不得盲目重放。

## 迁移与数据保护

- 各领域维护自己拥有的 schema、迁移文件和迁移记录；数据库基础设施按基础设施、Memory、Knowledge 的顺序确定性执行，单次迁移作为一个事务提交。
- 创建新数据库与打开已有数据库是不同操作。打开时必须识别可用状态与版本；数据库版本超出当前程序支持范围时，应停止并报告。
- 执行迁移前先创建 SQLite 一致性备份；在事务外关闭外键约束，并在提交前检查外键完整性。迁移失败时回滚并保留备份，不能通过删除、重建或重置用户数据伪装成成功。
- 索引重建只用于恢复派生索引，不能代替用户数据迁移或覆盖原始资料。
- 既有 PMEM 用户数据如何迁入新架构另行设计；此处不假设旧格式可以直接丢弃或自动迁移。

## 尚待确认

- Knowledge 文件适配器与数据库状态的协作、恢复和历史版本策略。
