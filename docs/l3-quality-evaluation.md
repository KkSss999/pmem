# L3 关键词提炼与检索质量评估

本文记录 L3 首版关键词提炼、L3-first 展开和降级行为的真实模型评估。评估使用 DeepSeek `deepseek-flash` 的 Chat Completions 接口和 L3 prompt `l3-v1`，不写入真实用户数据，也不代表生产质量已经达标。LongMemEval 首轮评测暴露的未解决问题和后续评测约束见 [Memory 已知问题记录](memory-known-issues.md)。

## 评估方法

- 在临时 SQLite 数据库中创建 L1、L2 和 L3 服务。
- 先用确定性 L1/L2 测试模型生成合成 L2，避免 L2 生成质量干扰 L3 评估。
- 再由真实 L3 模型从 L2 变化生成关键词。
- 使用相同的 L3 Service 执行生成、范围计算、来源合并、过期和 L3-first 展开。
- 查询分别使用 L3 关键词、别名和未生成关键词的主题，观察缓存命中、L2/L1 降级和事实返回。
- 记录 HTTP 状态、耗时、token usage 和模型原始输出。API Key 未写入仓库或数据库。

评估场景：

| 场景       | L2 数量 | 目标                             |
| ---------- | ------: | -------------------------------- |
| `project`  |       3 | 项目工具、待决策事项、角色和模块 |
| `personal` |       1 | 人物、地点、偏好和别名           |
| `noise`    |       1 | 一次性工作状态不应产生关键词     |
| `dedupe`   |       2 | 同一工具词跨 L2 合并来源         |

## 结果

### 生成结果

| 场景       | 任务        | 关键词 | 说明                                         |
| ---------- | ----------- | ------ | -------------------------------------------- |
| `project`  | `succeeded` | 5      | PMEM、SQLite、PostgreSQL、阿岚、记忆检索模块 |
| `personal` | `succeeded` | 3      | 阿岚、北城、拿铁（别名：拿铁咖啡、Latte）    |
| `noise`    | `succeeded` | 0      | 正确拒绝一次性代码提交状态                   |
| `dedupe`   | `succeeded` | 2      | SQLite 合并两个 L2 来源；FTS5 单独一条       |

所有成功调用的输出都通过了应用层校验，没有非法 `kind`、越权 L2、空来源或超长词。所有关键词范围都由来源 L2 的范围交集计算；`project` 场景的关键词范围为 `project + personal`，`personal` 场景为 `personal`。

### 检索结果

| 场景       | 查询           | L3 命中 | 返回                     |
| ---------- | -------------- | ------- | ------------------------ |
| `project`  | `SQLite`       | 是      | SQLite                   |
| `project`  | `PostgreSQL`   | 是      | PostgreSQL               |
| `project`  | `迁移`         | 否      | 降级 L2，返回迁移相关 L2 |
| `project`  | `记忆检索`     | 是      | 记忆检索模块             |
| `project`  | `阿岚`         | 是      | 阿岚                     |
| `project`  | `不存在的主题` | 否      | 降级 L1；没有 L2         |
| `personal` | `拿铁`         | 是      | 拿铁                     |
| `personal` | `北城`         | 是      | 北城                     |
| `personal` | `阿岚`         | 是      | 阿岚                     |
| `personal` | `咖啡`         | 是      | 通过别名命中拿铁         |
| `noise`    | `代码提交`     | 否      | 降级 L2，返回原始 L2     |

有明确预期的 11 次查询中，L3 命中 10 次，命中率约 91%；未命中的 `迁移` 正确降级到 L2，没有丢失事实。所有有结果的查询都返回了可读 L2，L3-first 结果同时牵出了 L1 和 L0 来源 ID。

### 调用成本与延迟

| 场景       |    耗时 | total tokens | prompt tokens | completion tokens |
| ---------- | ------: | -----------: | ------------: | ----------------: |
| `project`  | 2456 ms |         1378 |           938 |               440 |
| `personal` | 2660 ms |         1126 |           703 |               423 |
| `noise`    |  903 ms |          735 |           701 |                34 |
| `dedupe`   | 1492 ms |          994 |           810 |               184 |

成功调用平均约 1.9 秒、1058 tokens。样本很小，不能作为生产容量或成本结论。

## 发现

### 1. 关键词提炼基本可用

真实模型能稳定抽出人物、地点、工具、偏好和项目模块，能保留专有名词 `SQLite`、`PostgreSQL`、`FTS5`，能生成有价值的别名，也能对一次性任务状态返回空结果。

### 2. “迁移”这类主题词被漏掉

`PostgreSQL` 被提炼出来，但同一 L2 中“尚未决定是否迁移”的 `迁移` 没有成为关键词。查询仍然通过 L2 降级得到答案，但 L3 命中率下降。当前 prompt 偏保守，更偏向实体和工具；后续可在更大样本上评估是否明确要求保留稳定的动作、决策主题和状态概念。

### 3. 跨 L2 来源合并有效

`dedupe` 场景中，两个 L2 都提到 SQLite，最终只有一个 `SQLite` 关键词，并关联两个来源。没有产生重复关键词，也没有丢失第二个 L2。

### 4. 别名匹配可能偏宽

查询 `SQLite` 同时返回了 `SQLite` 和 `FTS5`，因为 `FTS5` 的别名是 `SQLite FTS5`，当前匹配包含子串。这个结果仍能召回正确 L2，但会增加候选噪声。后续需要评估精确词、别名和 FTS 的排序边界，不能只靠 top-k 掩盖误匹配。

### 5. 降级可用，但 L1 兜底可能过宽

`不存在的主题` 没有 L2，降级到 L1 后返回了 3 条 L1，因为合成 L1 的 abstraction 都使用了“主题”。这不是 L3 独有问题，但说明 L3 未命中后的 L1 兜底仍需要真实数据和排序/阈值评估。

### 6. 一次传输失败

第一次 `project` 调用使用 30 秒超时并返回 `API_TRANSPORT`，没有模型响应，3 个变更被标记为失败，没有写入假关键词。使用 60 秒超时重新运行时成功。该次失败可能是网络或超时，当前样本不足以判断稳定性；生产接入需要重试、超时和失败率观测。

## 限制

- 只有 4 个合成场景、4 次成功模型调用，样本不足以得出生产准确率。
- 没有人工相关性标注，命中率按预设查询统计，不等于真实召回质量。
- 没有覆盖长 L2、多语言混合、冲突事实、跨多个所有者空间和真实用户数据。
- 没有比较 L3-first 与 L2-only 的召回、延迟、token 和误召回差异。
- 没有评估 L3 默认启用阈值、top-k、TTL、权重和别名策略。
- L2 更新后的真实模型刷新、范围收窄和过期行为目前由针对性单元测试覆盖，未纳入本次真实模型评估。
- 一次传输失败未复现，失败率和重试策略尚未确定。

## 结论

首版 L3 已经能完成“从 L2 提炼短关键词 → 关键词命中 → 关联 L2 → L1/L0 展开”的闭环。人物、工具、偏好和跨 L2 合并场景表现符合预期，关键词不足时也能安全降级到 L2，而不是把关键词单独交给 Agent。

当前还不能据此默认开启 L3-first。下一步应扩大真实样本，分别评估提炼准确率、误召回、跨空间权限、L2-only 对照和默认策略；在得到对照结果前，L3 继续由调用方显式选择或灰度使用。
