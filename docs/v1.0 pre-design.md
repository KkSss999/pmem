# v1.0 前置设计决策：Agentic Memory Runtime

> 状态：draft → 待评审锁定
> 日期：2026-07-22
> 依据：用户架构决策（两层分离 + 项目记忆一等公民）

## 一、产品定位修正

v1.0 不再是"Project RAG OS"（把 pmem 从项目记忆工具改造成另一个方向），而是**把现有能力下沉成稳定内核，再在上面继续保留一个极其简单的 Coding Agent 使用体验**。

### 两层架构

```text
上层：开箱即用的项目记忆产品（CLI + Skills + MCP）
  → 普通用户和 Agent 框架依旧使用这一层
  → pmem init 就默认创建适合 Coding Agent 的标准配置

下层：可嵌入的 Agentic Memory Runtime（SDK / Runtime API）
  → 需要深度开发的人才直接调用
  → Miao、OpenClaw-like 产品或自研 Agent 系统
```

### 核心原则

> **默认极简，内部强大；项目记忆开箱即用，Agentic 能力按需开放。**

## 二、对现有用户：不应该变复杂

### 现有使用方式完全保留

```bash
npm install -g pmem-ai

cd my-project
pmem init
pmem install --skills --all
pmem use "继续开发认证模块"
```

然后 Claude Code、Codex、Gemini CLI、Cursor 等 Agent 通过规则文件、Skills 或 MCP 使用 pmem。

### 用户不需要理解的概念

以下概念由 `software` 项目预设自动配置，用户零感知：

- Memory Policy
- namespace
- event store
- scope inheritance
- storage provider
- SDK transaction

### 默认配置（开箱即用）

```yaml
preset: software

memory:
  default_scope: project
  branch_aware: true

  working:
    ttl: 12h

  episodic:
    capture: automatic

  durable:
    format: markdown
    confirmation: required
```

`pmem init` 一键生成，新的底层能力不转化成新的用户负担。

## 三、适配层架构

各个 Agent 框架仍然通过适配层接入，但逻辑统一落到底层 Runtime：

```text
Claude Code Skill ─┐
Codex Skill ───────┤
Gemini Skill ──────┤
Cursor Rules ──────┤
MCP Server ────────┤
OpenClaw Adapter ──┤
Miao Adapter ──────┤
LangGraph Adapter ─┤
                   ▼
             pmem Runtime API
                   ▼
          SQLite / Markdown / Graph
```

### 比现在更稳定的原因

- CLI 和 MCP 的查询结果一致（同一核心函数）
- 不同 Agent 看到相同的项目记忆
- 生命周期和权限规则统一
- 修复一次核心问题，所有适配器一起生效
- 不需要每个 Agent 框架单独实现召回和更新逻辑

## 四、三种集成深度

### 1. 零代码集成：Skills / Rules

适合 Claude Code、Codex、Gemini CLI、Cursor。

```bash
pmem install --skills --codex
pmem install --skills --claude
pmem install --skills --gemini
```

Agent 通过运行 CLI 使用 pmem。这是最简单、兼容性最强的模式，**长期保留**。

### 2. 标准协议集成：MCP

适合支持 MCP 的 Agent 框架。

```bash
pmem mcp
```

暴露工具：

```text
pmem_context    — 恢复项目上下文
pmem_recall     — 分层召回
pmem_ask        — 结构化查询
pmem_observe    — 观察变更（新增）
pmem_capture    — 捕获记忆（新增）
pmem_forget     — 移除记忆（新增）
```

框架不需要知道 pmem 内部实现。

### 3. 深度嵌入：SDK / Runtime API

适合 Miao、OpenClaw-like 产品或自研 Agent 系统。

```ts
const memory = await Pmem.open({
  root: projectRoot,
  preset: "software",
});

const context = await memory.context({
  task: "Implement authentication",
  budget: 2000,
});
```

这种模式允许产品自己控制 UI、工作流、权限和记忆策略。

## 五、项目记忆继续是一等公民

Agentic Memory Runtime 不意味着 pmem 要变成泛化的个人聊天记忆数据库。

```text
pmem Core
  └── 通用记忆能力（event store, scope, policy engine, storage providers）

pmem Software Preset
  └── 官方旗舰场景：项目记忆（获得最完整的支持）
```

### Software Preset 完整能力

- Git diff 感知
- branch scope
- source file path 检索
- module / decision / feature / task 卡片类型
- dirty card 生命周期
- trace capture（会话追踪）
- context restoration（上下文恢复）
- Agent rules 生成
- Coding Agent Skills 安装

其他 `research`、`novel` 或用户级记忆是扩展场景，不能削弱最核心的 Coding Agent 项目记忆体验。

## 六、兼容性原则（v1.0 硬约束）

### 1. CLI 不破坏

现有常用命令继续有效：

```bash
pmem ask
pmem recall
pmem context
pmem capture
pmem sync
pmem verify
```

底层实现可以重构，用户接口不随意变化。

### 2. Markdown 不破坏

现有 `.pmem/**/*.md` 仍然可读、可编辑、可 Git 管理。SDK 不能把用户强制迁移到黑箱数据库。

### 3. SQLite 仍可重建

即使增加 event log、working memory 或向量索引，SQLite 仍然是运行时状态，不是唯一事实源。`pmem rebuild` 必须能从 Markdown 完全重建 SQLite。

### 4. MCP 与 SDK 同语义

```text
CLI: pmem ask          →  memory.ask()
MCP: pmem_ask          →  memory.ask()
SDK: memory.ask()      →  memory.ask()
```

三者调用同一个核心函数，不是三套实现。

### 5. 默认配置保持简单

```text
默认：开箱即用（preset: software，零配置）
需要时：修改策略（manifest 中调整 memory policy）
深度集成：使用 SDK（Pmem.open() 直接编程）
```

复杂能力全部渐进暴露。

## 七、Runtime 如何让项目记忆更好

### 现在（v0.x）的问题

pmem 主要依赖 Agent：
1. 知道什么时候调用命令
2. 正确理解命令输出
3. 按流程更新记忆
4. 避免错误改写稳定卡片

### v1.0 Runtime 之后

框架只需要表达意图：

```ts
await memory.observe(change);       // pmem 自己决定放到哪个 scope
await memory.recall(query);         // pmem 自己负责召回策略
await memory.endSession(result);    // pmem 自己判断是否生成 trace
```

pmem 自己负责：

- 放到哪个 scope
- 是否生成 trace
- 是否命中重复内容
- 是否需要确认
- 是否应该蒸馏
- 哪些内容已经过期
- 哪些卡片应进入上下文

**Agent 集成更薄、更可靠。**

## 八、产品形态矩阵

| 使用者 | 接入方式 | 复杂度 |
|--------|----------|--------|
| 普通开发者 | CLI + Skills | 极低 |
| 支持 MCP 的 Agent | MCP | 低 |
| Agent 框架作者 | SDK | 中 |
| 深度基础设施开发者 | Runtime / Provider API | 高 |

## 九、不做的事情（防范围蔓延）

为了做通用平台而暴露大量抽象 → 让普通用户配置 scope、policy、provider → 最终失去 pmem 原本的轻量优势。**这是 v1.0 需要警惕的核心错误。**

v1.0 不做：

- ❌ 把 pmem 变成泛化个人聊天记忆数据库
- ❌ 要求普通用户理解 namespace / event store / scope inheritance
- ❌ 强制用户从 Markdown 迁移到黑箱数据库
- ❌ 为每个 Agent 框架单独维护一套召回和更新逻辑
- ❌ 暴露 storage provider 切换给终端用户

## 十、交付内容

v1.0 作为一个完整版本，一次性交付以下全部：

- **Runtime Core**：`Pmem.open()`、scope 管理、policy engine、event store（SQLite backed，Markdown 仍是 canonical）、working memory（会话级 TTL）、storage provider 接口（默认 SQLite + Markdown，可替换）
- **Unified Query Service**：CLI / MCP / SDK 三条路径统一调用同一 core 函数，`memory.ask()` = `pmem ask` = `pmem_ask`，消除 commands/ 和 core/ 之间的重复实现
- **Adapter Layer**：MCP server 改为调用 Runtime API（不再是独立实现），Skills 更新为调用统一 CLI，SDK 公开文档 + TypeScript 类型定义
- **Preset System**：`software` preset 作为默认 + 旗舰，`research`、`novel` preset 基于同一 Runtime，自定义 preset 机制
- **Migration & Compatibility**：v0.8 → v1.0 迁移路径，CLI 命令兼容性验证，Markdown 卡片格式不变，现有测试全部通过

## 十一、与 v0.8 的关系

v0.8（Hybrid Recall Engine）是 v1.0 的重要铺垫：

- v0.8 的 unified query engine（`src/core/query/engine/`）直接成为 v1.0 Runtime 的 query 层
- v0.8 的 L0-L3 分层渲染成为 `memory.recall()` 的输出格式
- v0.8 的 explain/reasons 机制成为 Runtime 的召回解释接口

v0.8 完成后，v1.0 的工作重点是：

1. 在 v0.8 query engine 之下增加 Runtime 层（scope、policy、event store）
2. 统一 CLI / MCP / SDK 三条调用路径
3. 保持上层用户体验不变
